# 知识库编写规范（模板）

本文件是 `kb/` 下所有规范文档的格式契约，也是一份可直接复制的模板。
**编写时严格照此格式**，因为下游有三处依赖：

1. `eval/run_eval.py` 依赖 `id` 字段做 ground truth 定位
2. 结构化校验通道依赖 `params` 字段做精确取值比对
3. 分块对比实验依赖正文的段落结构（标题层级）

---

## 一、为什么规范必须"可判定"

人类可读的规范文档和机器可判定的规则，差别只有一个词：**歧义**。

| ❌ 人类可读（不可判定） | ✅ 机器可判定 |
|---|---|
| 卡片内边距要合理，保持舒朗 | 内边距 ∈ {12, 16, 24}，按卡片类型映射 |
| 文字要保证可读性 | 正文对比度 ≥ 4.5:1；大号文字（≥18px 或 14px 粗体）≥ 3:1 |
| 标题层级要清晰 | 字号 ∈ {12,14,16,20,24,32}，标题仅用 20/24，展示型用 32 |
| 命名要规范 | 属性名 camelCase；布尔属性以 is/has/can 开头 |

可判定的三个必要条件：
- **具体值**：能枚举就枚举，不能枚举就给数值区间
- **适用条件**：说明"什么情况下这条规则生效"
- **例外**：说明"什么情况下允许违反"，没有例外就写"无"

缺任何一条，模型就只能靠猜 —— 而"猜"正是误报和漏报的根源。

## 二、文件格式契约

每个 `kb/*.md` 文件 = **YAML front-matter（结构化通道）+ 正文（叙事通道）**。

### 2.1 front-matter 字段（全部必填）

```yaml
---
doc_id: spacing                    # 文件名同名，英文小写
title: 间距规范
version: 1.0
scope: 所有界面组件的间距取值与用法

rules:
  - id: SPACING-001                # 唯一标识，见第三节的 ID 分配表
    title: 卡片内边距取值           # 6-14 字，能被单独引用
    statement: >                   # 一句话的判定规则，必须可执行
      卡片内边距只允许 12 / 16 / 24 三档，按卡片类型映射，禁止其他档位。
    params:                        # 结构化参数：精确校验靠它
      allowed: [12, 16, 24]        # 允许值枚举
      mapping:                     # 按场景映射（可选）
        compact_list: 12
        regular_content: 16
        marketing: 24
    applies_when:                  # 适用条件：什么情况下这条生效
      - 组件类型为卡片（Card）
    exceptions:                    # 例外：没有就写「无」
      - 全屏沉浸式视图内的卡片不受此限制
    positive_case:                 # 合规示例
      desc: 常规内容卡片设置内边距 16px
      value: 16
    negative_case:                 # 违规示例（必须具体到值）
      desc: 常规内容卡片设置内边距 20px
      value: 20
      expected_verdict: fail
    rationale: >                   # 为什么这么规定（给人和模型理解用）
      三档阶梯覆盖紧凑/常规/宽松三种信息密度；引入第四档会让同层级卡片
      在没有设计意图的情况下出现视觉差异。
---
```

### 2.2 字段说明与硬性要求

| 字段 | 要求 |
|---|---|
| `id` | 唯一，格式 `<CATEGORY>-<三位序号>`，全局不可重复 |
| `title` | 6-14 字，必须能脱离上下文单独被引用 |
| `statement` | 一句话，含具体值或数值区间，**不含"合理""适当""尽量"等模糊词** |
| `params` | 结构化取值。类型可为 `allowed`（枚举）/ `range`（区间）/ `pattern`（正则）/ `mapping`（场景映射） |
| `applies_when` | 列表，至少 1 条。写清触发条件，不能写"所有情况" |
| `exceptions` | 列表。真的没有例外时写 `- 无`，不要留空 |
| `positive_case` | 必须给出**具体值**，不能写"符合规范的做法" |
| `negative_case` | 必须给出**具体值** + `expected_verdict: fail` |
| `rationale` | 说明设计意图。这是模型能做出合理"建议修改"的依据 |

### 2.3 正文（front-matter 之后）

正文是通道 A，会被三种分块策略切分。结构要求：

- **每个 `## 二级标题` 对应一条规则**，标题文字与 `title` 保持一致
- 标题下先写"规则说明"段落（2-4 句，讲清规则本身）
- 再写"为什么"段落（设计意图）
- 再写"正反例"（具体值）
- **不要在正文里重复 front-matter 的字段名**，正文要像真实规范文档那样行文

这样设计的理由：标题分块策略会以 `##` 为切分点，
标题与 `title` 一致才能保证"检索命中 → 规则 id"可对齐。

### cases（历史违规案例）— `kb/cases.md` · `CASE-001..015`

这条通道与上面不同：**它不是规则，而是"违规 → 修正"的真实案例记录**，
用于让检索结果里带有"以前踩过的坑"这类上下文。

格式：

```yaml
---
doc_id: cases
title: 历史违规案例库
version: 1.0
scope: 过往评审中发现并修正的真实违规记录

cases:
  - id: CASE-001
    title: 卡片内边距使用 20px
    rule_ref: SPACING-001          # 违反的规则 id，必须存在于上面的规则表
    violation: 常规内容卡片内边距设为 20px
    impact: 与同页面其他卡片产生 4px 视觉差异，栅格对齐被破坏
    fix: 改为 16px，并与同组卡片保持一致
    lesson: 20px 是"看起来差不多"的典型陷阱，必须查表而非凭感觉
---
```

`rule_ref` 必须引用已存在的规则 id，且 15 条案例要**覆盖全部 5 个类别**
（spacing ≥3、color ≥3、typography ≥3、component ≥3、naming ≥3）。

## 四、一份完整的示例（照这个水准写）

见 `kb/spacing.md` —— 它是本次生成的标准样板，其余文件请对齐它的颗粒度：
- 每条 `statement` 都能被逐字判定
- 每个 `negative_case` 都有具体数值
- 每个 `rationale` 都讲出了设计意图，而不是复述规则
