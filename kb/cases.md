    title: 卡片内边距使用 20px
    rule_ref: SPACING-001
    violation: 数据概览页「本月订单」卡片内边距被实例级覆盖为 20px，同组其余三张卡片为 16px。
    impact: 该卡片上下各多出 4px，同一行四张卡片顶部对齐但底部参差不齐，页面右侧栅格基准被挤偏 4px；前端照稿实现后设计走查打回一次，返工约半天。
    fix: 清空该实例的 padding 覆盖项，回到 Card/regular-content 主组件的 16px，并逐页检查卡片实例是否残留同类覆盖。
    lesson: 20px 是「看起来差不多」的典型陷阱，间距必须查表，不能凭手感微调。

  - id: CASE-002
    title: 同组卡片间距混用 16 与 24
    rule_ref: SPACING-002
    violation: 设置页「账号」「通知」「隐私」三张卡片属同一组，账号与通知之间为 16px，通知与隐私之间为 24px。
    impact: 用户把「通知」读成与「隐私」同组，设置项归属被误判，客服收到「找不到隐私设置」的反馈；前端也因两种间距而写死两个 margin，后续增删卡片必错。
    fix: 同组三张卡片间距统一为 16px；若确实要突出「隐私」的独立性，应新增分组标题，并把组间距改为 24px。
    lesson: "组内间距一旦混用，用户就会自己发明分组逻辑，而这个逻辑永远不会和设计意图一致。"

  - id: CASE-003
    title: 组间间距等于组内间距
    rule_ref: SPACING-003
    violation: 仪表盘「概览」与「明细」两个分组，组内 16px、组间也沿用列表组件的 16px。
    impact: 两个分组被读成一条 8 张卡片的连续列表，信息架构中「概览 / 明细」的层级在视觉上完全消失，评测中用户无法复述页面结构。
    fix: 组间距改为 24px，确保严格大于组内 16px 且不低于 24；同时可在两组之间补一行分组标题强化边界。
    lesson: "组间必须严格大于组内——两者相等，等于没有分组。"

    lesson: "色阶变量是调色板，不是接口；组件只能依赖语义令牌。"

    rule_ref: TYPO-002
    violation: 14px 正文行高设为 1.4（即 19.6px，实现时取整为 20px）。
    impact: 三行以上的说明段落行距偏紧，长文阅读明显疲劳；同一页面另一处长文按 1.5 计算得 21px，出现两种行高，段落节奏不一致且无法用一套样式覆盖。
    fix: 行高统一为字号 × 1.5，14px 对应 21px，并在文本样式中以倍数定义而非写死像素值。

    impact: show-icon 与「是否禁用」都无法直接映射为合法代码标识符，代码生成后需人工逐个改名，前端为对齐属性多花近半天，且改名过程中漏掉一处导致图标未渲染。

    fix: 按 PascalCase 重命名为 PrimaryButton 与 IconButton，在组件面板中合并重复项并同步更新引用页面。
    lesson: "命名风格分叉的代价不在命名本身，而在于它让同一个组件在库里存在两份。"

    lesson: "令牌名要同时被人和工具消费，任何大小写歧义迟早会变成一次线上事故。"

# 历史违规案例库

本文件记录过往设计评审中发现并已修正的真实违规。每条案例都能追溯到一条现行规则。
规则告诉你「应该是什么」，案例告诉你「不这么做会发生什么」——后者是模型与新人最快
建立判断力的材料。

案例按类别分组编号，每三条一组：`CASE-001` 至 `CASE-003` 为间距，`CASE-004` 至
`CASE-006` 为色彩，`CASE-007` 至 `CASE-009` 为字体，`CASE-010` 至 `CASE-012` 为
组件属性，`CASE-013` 至 `CASE-015` 为命名。每组第一条是该类别中出现频次最高的违规。

## 卡片内边距使用 20px

> 案例编号 CASE-001 ｜ 违反规则 SPACING-001

**问题描述。** 数据概览页的「本月订单」卡片在实例上把内边距手动覆盖成了 20px，
同组另外三张卡片仍是 16px。改动原因很偶然：设计师当时觉得这张卡片「挤了一点」。

**影响。** 20px 让这张卡片上下各多出 4px，同一行四张卡片顶部对齐、底部参差，
右侧栅格基准被挤偏 4px。前端照稿实现后，设计走查打回一次，返工约半天；
更麻烦的是这类覆盖不会出现在主组件上，后续无人知道它从哪来。

**修正。** 清空该实例的 padding 覆盖项，回到主组件的 16px，并逐页检查卡片实例
是否残留同类覆盖。若确实需要更宽松的呼吸感，应按卡片类型走 24px 档，而不是造新档位。

**经验。** 20px 是「看起来差不多」的典型陷阱，间距必须查表，不能凭手感微调。

## 同组卡片间距混用 16 与 24

> 案例编号 CASE-002 ｜ 违反规则 SPACING-002

**问题描述。** 设置页的三张卡片「账号」「通知」「隐私」属于同一组，但账号与通知之间
是 16px，通知与隐私之间是 24px。差异来自两次不同时间的修改，没有被复查。

**影响。** 用户把「通知」读成了与「隐私」同组，设置项的归属被误判，客服收到
「找不到隐私设置」的反馈。前端也因为两种间距而写死两个 margin，之后增删卡片必然出错。

**修正。** 同组三张卡片统一为 16px。如果确实要突出「隐私」的独立性，正确做法是
新增分组标题，并把组间距改为 24px，而不是靠一个不对齐的缝隙暗示。

**经验。** 组内间距一旦混用，用户就会自己发明分组逻辑，而这个逻辑永远不会和设计意图一致。

## 组间间距等于组内间距

> 案例编号 CASE-003 ｜ 违反规则 SPACING-003

**问题描述。** 仪表盘的「概览」与「明细」是两个业务分组，组内 16px，组间也沿用了
列表组件的 16px，原因是直接复用了同一个间距工具类。

**影响。** 两个分组被读成一条 8 张卡片的连续列表，信息架构中「概览 / 明细」的层级
在视觉上完全消失。可用性测试中用户无法复述页面结构，只说「这里有很多卡片」。

**修正。** 组间距改为 24px，确保严格大于组内间距且不低于 24；必要时再补一行分组标题，
让分组边界同时具备间距信号和文字信号。

**经验。** 组间必须严格大于组内——两者相等，等于没有分组。

## 灰色正文对比度不足 4.5:1

> 案例编号 CASE-004 ｜ 违反规则 COLOR-001

**问题描述。** 卡片的辅助说明文字（如「上次更新 3 天前」）使用 #767F8C 灰，
置于 #FFFFFF 白底，实测对比度约 4.1:1。它是从一次「让界面更轻盈」的调整里带进来的。

**影响。** 浅色主题下这行文字在普通办公显示器上难以辨认；无障碍扫描报出正文对比度
不达标，可用性验收被卡住，文案组被迫删减说明文字来规避问题。

**修正。** 改用更深一档的中性文字语义令牌，保证对比度不低于 4.5:1，并在样式层
以令牌引用，禁止再出现写死的十六进制灰。

**经验。** 差 0.4 的对比度肉眼几乎看不出来，但它是达标与不达标的分界线，必须实测。

## 按钮组件未声明 size 与 variant

> 案例编号 CASE-010 ｜ 违反规则 COMP-001

**问题描述。** Button 组件在新增实例时没有显式声明 size 与 variant，只保留了默认外观，
交付说明里也没有标注实际取值。

**影响。** 前端只能按视觉猜测实现，猜中的尺寸与设计稿实际使用的并不一致，登录页三个
按钮高度全部偏差，联调阶段返工一次。

**修正。** 在组件属性面板显式设置 size 与 variant 并写入交付说明；评审时对缺失这两个
声明的实例直接判定不合规。

**经验。** 没写出来的属性等于不存在——组件契约必须显式，不能靠外观倒推。

## 属性名混用 kebab-case 与中文

> 案例编号 CASE-011 ｜ 违反规则 COMP-002

**问题描述。** 同一个组件的属性同时出现了 show-icon、loading_text 和中文属性名
「是否禁用」三种写法，分别由三位设计师在不同时间添加。

**影响。** show-icon 与「是否禁用」都无法直接映射为合法代码标识符，代码生成后需要
人工逐个改名，前端为对齐属性多花了近半天；改名过程中漏掉一处，导致图标未渲染。

**修正。** 全部改为 camelCase，即 showIcon、loadingText、isDisabled，并在组件文档中
固化命名示例供后续新增属性参照。

**经验。** 属性名是给代码用的接口，不是给人看的标签，格式必须从第一天就统一。

## 布尔属性缺少 is 前缀

> 案例编号 CASE-012 ｜ 违反规则 COMP-003

**问题描述。** Tab 组件的布尔属性被命名为 disabled 与 active，没有使用 is / has / can 前缀。

**影响。** 属性面板里布尔属性与字符串属性无法一眼区分，调用方把 active 误传为字符串
"true"，Tab 高亮态在部分浏览器上未生效，问题一直到提测后才暴露。

**修正。** 重命名为 isDisabled 与 isActive，并在组件文档中标注布尔类型，
避免调用方再传字符串。

**经验。** 前缀是类型的自述；省掉三个字母，换来的是调用方对类型的持续猜测。

## 组件命名使用 kebab-case

> 案例编号 CASE-013 ｜ 违反规则 NAME-002

**问题描述。** 组件库中新组件被命名为 primary-button 与 icon_button，与既有的 Card、
Modal 形成两套命名风格。

**影响。** 搜索时 PrimaryButton 与 primary-button 同时出现，设计师各自实例化，
一个迭代后库里存在两套按钮；样式修改要改两处，维护成本翻倍。

**修正。** 按 PascalCase 重命名为 PrimaryButton 与 IconButton，在组件面板中合并重复项，
并同步更新所有引用页面。

**经验。** 命名风格分叉的代价不在命名本身，而在于它让同一个组件在库里存在两份。

## 交付文件中残留 Frame 123

> 案例编号 CASE-014 ｜ 违反规则 NAME-003

**问题描述。** 交付页面残留 27 个默认图层名，包括 Frame 123、Rectangle 47、Group 8、
Ellipse 12，且正好覆盖了弹窗与表单等关键结构。

**影响。** 开发在标注阶段无法判断 Frame 123 与 Frame 124 谁是弹窗容器，三次截图询问
设计师，标注沟通多花一小时；图层结构也无法被自动化脚本解析，设计资产的复用价值归零。

**修正。** 导出前重命名关键图层，至少覆盖容器、列表项与状态层，并用命名检查插件
做一次全量扫描。

**经验。** 图层名是设计稿里唯一能被机器读懂的语义，默认名等于把语义全部丢弃。

## 设计令牌命名不符合 kebab-case

> 案例编号 CASE-015 ｜ 违反规则 NAME-004

**问题描述。** 令牌命名同时存在 PrimaryBlue、colorPrimary 与 Color-Primary-500
三种风格，大小写与连接符都不统一。

**影响。** 令牌导出为 JSON 后大小写不一致，前端无法用统一规则批量生成样式变量；
PrimaryBlue 与 primaryBlue 在大小写不敏感的工具链中互相覆盖，最终生效值不确定，
线上出现过一次颜色「随机」变化。

**修正。** 统一为 kebab-case 的「类别-语义-变体」结构，例如 color-primary-default
与 color-primary-hover，并重新导出令牌包。

**经验。** 令牌名要同时被人和工具消费，任何大小写歧义迟早会变成一次线上事故。
