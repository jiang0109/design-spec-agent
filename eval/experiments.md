## 实验 1：溯源漂移 —— 模型会改写引用出处

### 现象

检查 `out/*.report.json` 时发现，`evidence_sections` 字段里的出处与
`search_spec` 实际返回的 section 不一致：

| 检索实际返回 | 模型写入 evidence_sections |
|---|---|
| `color.md#语义色` | `color.md#语义色的使用` |

核心判据本身没错 —— `evidence` 里的规范原文是逐字准确的；
出问题的只是"出处标签"这一个字段，模型**顺手把它扩写了**。

### 为什么这算缺陷

`evidence` 是给人和模型看的，而 `evidence_sections` 是**给程序用的**。
它的用途是"结论 → 规范条目"的反向索引：当某条规范被修改时，
需要靠它批量找出所有可能失效的历史结论。

标签一旦被改写，这个索引就断了 —— 而且是**静默断裂**，
不会报错，只会让你在某天发现检索不到本该命中的结论。

### 预期

加严提示词（明确禁止改写 + 给出正确方向的示例）后，漂移率应显著下降。

### 实际

同一份文档、同一温度，分组重复采样。`n=5` 与 `n=10` 两轮独立复现，方向一致：

| 组别 | 表述 | 漂移次数 | 漂移率 |
|---|---|---|---|
| 对照组 | `REPORT_INSTRUCTION_LOOSE`（修复前） | 2 / 5 | 40% |
| 实验组 | `REPORT_INSTRUCTION`（加严后） | 0 / 5 | 0% |
| **对照组（扩样）** | 同上 | **5 / 10** | **50%** |
| **实验组（扩样）** | 同上 | **0 / 10** | **0%** |

合计：修复前 **7/15 = 47%**，修复后 **0/15 = 0%**。

**统计口径说明**：`n=5` 时 40% 这个点估计不稳定，扩到 `n=10` 后落在 50%。
两轮都观测到"修复后 0 次漂移"，合计 0/15 —— 可以合理认为修复后漂移率
显著低于修复前，但**不能据此宣称"已彻底消除"**：
15 次全零只说明真实漂移率大概率低于约 20%（3/n 经验上界），
不足以证明为 0。要给出更紧的界需要更大的样本量。

### 复现方式

```powershell
python -m eval.probe_experiments -n 10 --only drift
```

### 排查过程中的两个自身 bug（这部分比结论更重要）

第一次运行得出的结果是 **"修复前 40% → 修复后 100%"** —— 方向完全反了。
如果当时直接采信这个数字，会得出"加严提示词有害"的错误结论并回滚修复。
排查后发现两个 bug 都在我自己这边：

**Bug A：加严提示词里的示例方向写反了**

知识库（`src/tools.py`）里实际定义的是：

```python
"section": "color.md#语义色",   # 短标签
```

而我写的示例是：

```
返回 "color.md#语义色的使用" 时，不得写成 "color.md#语义色"
```

等于**亲手教模型去扩写**。改成正向示例（"返回 `color.md#语义色` 就必须原样写"）
之后，漂移率立刻降到 0%。

**Bug B：提取器的字段名写错，导致指标本身是假的**

```python
hit.get("section")        # ← 错的
hit.get("section_id")     # ← schema 里实际叫这个
```

于是"实际检索到的 section 集合"恒为空集，漂移判定退化成纯噪声。

### 结论与教训

1. **先验证指标，再相信指标。** 一个错误的度量比没有度量更危险 ——
   它会让你朝错误方向优化，而且看起来"有数据支撑"，更难被质疑。
2. 修复动作现在是可验证的：`provenance_checked` 字段会显式暴露
   "本次检测是否可信"。指标不可信时必须暴露，不能静默返回假结果。
3. 提示词里的示例会被模型当作强信号。**示例写错 = 主动引入缺陷**，
   这与"示例要覆盖边界情况"是同一件事的两面。

> ⚠️ 未解决：当前只在单个用例、单一文档上验证。Week 2 建评测集后，
> 应把漂移率纳入常规回归指标，并在多样本文档上复测 ——
> 单文档 + 小样本的结论不能外推到真实规范库。

## 实验 2：工具调用总预算 —— 补齐 `max_steps` 拦不住的漏洞

### 现象

`--max-steps 1` 确实触发了强制终止，但模型**在唯一那一轮里并发发出了 6 个工具调用**：

```
[step 1] 调用 search_spec('卡片内边距允许哪几档')
[step 1] 调用 search_spec('卡片之间的间距规范')
[step 1] 调用 search_spec('主按钮文字颜色规范')
[step 1] 调用 search_spec('按钮 variant 属性默认值要求')
[step 1] 调用 search_spec('页面标题字号规范')
[step 1] 调用 search_spec('标题行高规范')
[warn] 达到 max_steps=1，强制终止工具循环
```

### 为什么这算缺陷

`max_steps` 限制的是**轮次**，不是**调用次数**。模型一次可以并发几十个调用，
`max_steps=1` 一个都拦不住。**真正的成本护栏必须是调用总数。**

这是"如何防止费用失控"这个问题的关键 —— 只答"我设了 max_steps"是不完整的。

### 预期

把预算压到 2（文档实际需要 6 次查询）后：
- 第 3 个及以后的调用被拒绝，并告知模型
- 模型停止检索，对已查到依据的点正常判定
- **对未查到依据的点判 `uncertain` 且不编造**

### 实际

`python cli.py samples/sample_doc.md --tool-calls 2 -v`

```
[step 1] 调用 search_spec('卡片内边距允许哪几档')
[step 1] 调用 search_spec('卡片之间的间距规范')
[step 2] 模型结束工具循环，进入结构化输出
[report 1/3] 校验通过，共 6 条判定
```

| 指标 | 结果 |
|---|---|
| 实际工具调用 | 2 次（严格等于上限） |
| `budget_exhausted` | `true` |
| 溯源漂移 | 无 |
| 已查到依据的 2 点 | 正常判定（1 fail / 1 pass，与全预算时一致） |
| 未查到依据的 4 点 | **全部 `uncertain`，`evidence` 留空** |
| 疑似编造（有判定但无依据） | **0 条** |

报告里模型的自述印证了它理解了预算语义：

> 其余 4 项（主按钮文字色、按钮 variant 默认值、页面标题字号、标题行高）
> 因检索预算耗尽未取得规范依据，判 uncertain，不作合规结论。

### 复现方式

```powershell
python cli.py samples/sample_doc.md --tool-calls 2 -v
python -m eval.probe_experiments --only budget
```

### 结论

1. 预算护栏按设计工作：**拒绝要显式回填给模型**，而不是静默丢弃 ——
   模型需要知道"为什么查不到了"，才能正确降级。
2. 更重要的一点：**预算不足时的行为是"诚实降级"而不是"猜测补全"。**
   这是可控性的核心，也是这套系统敢用在真实规范审查上的前提。
3. 两道护栏各管一件事，缺一不可：
   - `max_steps`（默认 6）→ 防"反复查同一条"的死循环
   - `max_tool_calls`（默认 12）→ 防"单轮并发几十个调用"的费用失控

## 实验 3：无依据时是否编造 —— 反幻觉验证

### 现象/预期

构造一条知识库**完全没有覆盖**的规范（`samples/no_rule_doc.md`：图标按钮圆角 6px），
观察模型是会老实说"查不到"，还是会编造一条"圆角规范"出来。

### 实际

```json
{
  "verdict": "uncertain",
  "evidence": "",
  "evidence_sections": []
}
```

三个细节都符合预期：
1. **没有硬判 `fail`** —— 没有把"6px 不在某档"当成违规
2. **`evidence` 留空** —— 没有编造规范条文
3. **`evidence_sections` 为空** —— 没有伪造出处

额外观察：模型**主动检索了两次**（换了个查询措辞再试），
不是查一次失败就放弃；并在结论里给出建设性反馈：
"建议补充相关组件的圆角规范后再行审查"。

### 复现方式

```powershell
python cli.py samples/no_rule_doc.md -v
```

### 结论

系统提示里的判定纪律（"宁判 uncertain，不判错；检索不到依据绝不凭记忆猜测"）
是可生效的，不是摆设。这条对这类产品的意义：**知识库有覆盖盲区是常态，
agent 必须能表达"我不知道"，否则会持续产出看起来合理但错误百出的判定。**

## 实验 4：Windows 中文控制台编码陷阱（工程坑，非 agent 问题）

### 现象

运行报告打印时程序**部分输出后中断**：文件已写出，但终端看不到报告内容。

### 根因

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u274c' in position 261
```

`\u274c` 是报告里的 ❌。Windows 中文控制台默认 GBK 编码，无法编码该字符，
`print(render_markdown(ar))` 直接抛异常。

### 修复

在 `cli.py` 入口处把标准流强制为 UTF-8：

```python
for _stream in (sys.stdout, sys.stderr):
    try:
        _stream.reconfigure(encoding="utf-8", errors="replace")
    except (AttributeError, ValueError):
        pass
```

### 为什么记录它

这个 bug **伪装成"agent 跑挂了"**：报错栈指向 `render_markdown`，
看起来像渲染逻辑有问题，实际与 agent 逻辑毫无关系。
"看起来是 A 问题、实际是 B 问题"的排查过程，是工程能力最真实的体现。

## 附：Week 1 基线性能数据

| 用例 | 工具调用 | token（入+出） | 耗时 |
|---|---|---|---|
| `sample_doc.md`（6 个判定点，全预算） | 6 | 5112 + 1646 | 17.6s |
| `sample_doc.md`（`--max-steps 1`） | 6 | 2685 + 1041 | 6.4s |
| `sample_doc.md`（`--tool-calls 2`） | 2 | 4608 + 1250 | 7.2s |
| `no_rule_doc.md`（无依据） | 2 | 2327 + 413 | 5.2s |

**注意 1**：文档只有 255 字符，却消耗约 6800 token。原因是每次检索固定返回
top-3 条目，6 次检索把 18 条规范原文全塞进上下文，冗余很高。
**这是 Week 2 的优化目标** —— 分块 + rerank 之后应显著下降。

**注意 2**：单次运行的 token 波动较大（同一用例 4988 / 5112 两轮），
所以任何优化都必须**多次采样取均值**，不能拿两次单跑数字对比。
这一点同样适用于实验 1 的样本量选择。

**注意 3**：实验 1 扩样到 `n=10` 后额外消耗约 140k token（两组合计）。
做对照实验要提前估算成本 —— 但也别为了省钱把样本量压到没有统计意义，
那样得到的"结论"比不做实验更危险。

## 下一步（Week 2 起纳入回归的指标）

| 指标 | 当前值 | 目标 |
|---|---|---|
| 溯源漂移率 | 修复前 47%（7/15）→ 修复后 0%（0/15） | 保持 0，并在多文档上复测 |
| 检索 Recall@5 | 未测量（检索是关键词占位实现） | ≥ 0.7，并给出分块/重排消融对比 |
| 端到端判定准确率 | 未测量（单一用例 6/6） | ≥ 85%，误报率 ≤ 10% |
| 单用例 token 消耗 | 约 6800（255 字符文档） | 通过收窄检索结果显著下降 |

**当前最大的空白：检索质量完全没有度量。** Week 1 的关键词打分能命中
是因为知识库只有 8 条 —— 这个规模下几乎怎么查都能中，检索问题被掩盖了。
知识库扩到真实规模（数百条）后，"查得准不准"才会成为主要瓶颈。
