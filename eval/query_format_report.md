# 实验报告：约束查询表述

**任务**：agent 会发出"允许哪几档""应使用哪个色阶变量""是否与内容一致"这类
**预设了知识库不支持的框架**的查询，导致规则匹配偏移。约束它的查询格式。

**结论：指令本身完全生效（预设框架查询 0%），准确率从 96% 降到 95%，
但错误画像从「漏报」转向「过度拒答」—— 对合规检查工具这是更安全的失败方式。**

复现：`python -m eval.run_generation_eval`（115 份文档 / 120 判定点，约 14 分钟）

---

## 一、改了什么

### 1. 系统提示的「检索纪律」新增约束

```
- 查询写成「对象 + 属性 + 取值」，直接陈述要检查的事实，
  例如 "卡片内边距 20px"、"正文行高 1.4 倍"、"图层名 Rectangle 45"。
- 不要在查询里预设答案的形式，也不要引入规范未定义的判断维度。
    问"允许哪几档" —— 若规范只给下限而没有档位，就无从匹配
    问"应该用哪个变量" —— 若规范恰恰禁止使用那类变量，问题就预设反了
    问"是否与内容一致" —— 这是规范未定义的维度，没有规则能回答
```

### 2. 工具参数的描述同步改写（决策点附近再提醒一次）

### 3. 新增查询日志（关键）

`AgentReport` 新增 `retrieval_queries` 字段，记录 agent **实际发出的每条查询**。

> 加这个字段的直接动因：上一轮我把"判定器太严格"当根因，是因为**看不到它到底问了什么**。
> 查询语句是"适用性判定"的输入，输入不可观测时，任何结论都只能靠猜。

## 二、指令确实生效了

| 指标 | 结果 |
|---|---|
| 查询总数 | 143 |
| **带预设框架措辞的查询** | **0（0%）** |

实测查询样例全部变成陈述式：

```
✓ 紧凑列表卡片内边距 12px
✓ 营销位卡片内边距 20px
✓ 同一组卡片之间的间距 16px
✓ 表头与首行数据之间的间距 12px
```

**这是本轮唯一确定性成立的结论** —— 提示词被严格执行了。

---

## 三、结果：准确率略降，但错误画像换了

| 指标 | v4（无约束） | v5（有约束） |
|---|---|---|
| 端到端准确率 | 96%（115/120） | **95%（114/120）** |
| 误报 FP | 0 | 0 |
| **漏报 FN（违规判成合规）** | **3** | **0** |
| **过度拒答（判 uncertain）** | **0** | **4** |
| 过度自信（无覆盖下结论） | 2 | 2 |

**错误的性质整体从"危险"移到了"安全"：**

- **漏报**：违规被判成合规 → 问题流到线上，用户看到错的界面
- **过度拒答**：说"知识库无法判定" → 人工复核一次，**不产生错误结论**

对一个合规检查工具，**后者是更可接受的失败方式**。

## 四、机制：4 处新误拒，两类原因

| 案例 | 实际查询 | 原因 |
|---|---|---|
| E030 | 文章正文文字字号 14px | **检索偏了** —— 召回的是对比度规范（COLOR-001/002），不是字号规范（TYPO-001） |
| E037 | 区块标题行高 34px | **检索漏了** —— 直接 no_coverage，TYPO-002 未进候选 |
| E013 | 内容区最大宽度 1440px | 召回到 SPACING-004，但判定器判"讲的是页面外边距，不是最大宽度" |
| E024 | 分隔线颜色引用 gray-300 色阶变量 | 召回到 COLOR-003，但判定器判 not_applicable |

**根因是查询变短导致 BM25 召回变差**：陈述式查询（"文章正文文字字号 14px"）
比原来的问句（"文章正文文字字号允许使用哪几档"）**少了"允许/哪几档"这类词**，
但更要紧的是——它把重心压在"文字"上，而"文字"在对比度规则里高频出现，
于是**检索被拉到对比度规范上**。

> 这是一个没预料到的耦合：**约束"提问框架"的同时，也削弱了"检索特征"。**
> 短查询更精确，但 BM25 是词频驱动的，短查询给它的抓手更少。

---

## 五、两处过度自信：同一场景被计两次 + 通用规则被过度套用

`G34`（表头与首行间距 12px）与 `E078`（表格表头与首行间距 12px）是**同一个场景**，
两次运行都判 pass，理由都是：

> "12px 属于规范规定的 4 的整数倍间距取值集合（4/8/12/16），符合要求"

**这是把 `SPACING-005`（组件内部元素间距）套用到了"表头与首行之间的间距"上。**
严格讲表头与首行不属于"组件内部元素"，规则不覆盖。模型做了**过度适用**。

值得注意：**这正是我在 v3 判定器里预判过的"aspect 过度放宽"风险，
现在出现在了生成层。** 说明这个风险是整条链路的共性，不只是判定器的。

另外评测集该去重：`G34` 与 `E078` 是同一场景，现在被计为 2 个错误，**放大了单一缺陷的权重**。

---

## 六、判断：保留这个改动

### 理由

1. **指令可验证地生效**（0% 预设框架），这是查询卫生的实质改善。
2. **漏报归零**。对合规工具，漏报是最严重的错误类型 —— 它让规范形同虚设。
3. **新的错误都是"说不确定"**，不产生错误结论，只是增加人工复核量。
4. 1pp 的准确率下降来自**检索召回**，是可单独修的（见下），不是格式约束本身的固有代价。

### 代价要承认

- 准确率 96% → 95%
- 过度拒答 0 → 4（可用性下降）
- 这两点必须写在 README 里，不能只报"漏报归零"

## 七、下一步

| 顺序 | 动作 | 依据 |
|---|---|---|
| **1** | **让查询兼顾"陈述事实"与"检索特征"** | 现在短查询丢失检索抓手（E030/E037）；可要求"对象+属性+取值 + 所属组件/场景"，例如 "卡片 内边距 20px" |
| 2 | 评测集去重（G34/E078） | 单一缺陷被计两次 |
| 3 | 修生成层的"通用规则过度套用" | 表头间距被按组件内部间距判 pass |
| 4 | 规则引擎接管判定步骤 | 覆盖 75% 判定点，消除"算错"类波动 |

### 一个待验证的具体设想

把查询格式从「对象 + 属性 + 取值」放宽为「**场景/组件 + 对象 + 属性 + 取值**」：

```
现在  "文章正文文字字号 14px"        → "文字"主导，召回到对比度规范
设想  "文章正文 字号 14px"            → 保留"文章正文"，但让"字号"成为主词
```

这个方向能同时保住查询卫生与检索召回，但**必须用完整 120 点评测验证** ——
本轮已经证明：局部改善很容易在另一侧带来回归。
