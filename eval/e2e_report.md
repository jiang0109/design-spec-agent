# 端到端验证报告：检索层拒答接入后的真实表现

**要做的事**：把 `relevance_report.md` 验证过的 LLM 相关性闸门接入 `search_spec`，
然后端到端检验"检索层拒答 + 生成层 uncertain"这条链路是否真的减少幻觉。

**结论：拒答接入**完全阻断**了编造，但代价是一次**真实的功能回归** ——
它把一个本该判 fail 的点误拒成了 uncertain。净收益在当前证据下不成立。

复现：`python -m eval.run_e2e`（真实 API 调用，约 6 次 agent 运行）

---

## 一、接入实现

### 两级检索（成本控制）

相关性判定每题 k 次 API 调用，是 BM25 的数十倍成本，所以分两级：

```
阶段 1  BM25 粗排 top-10   （便宜）
阶段 2  只对最靠前的 top-2 做 LLM 相关性判定（贵）
阶段 3  relevance >= 2 才返回；一条都没有则返回 found=false 并明确告知"知识库无覆盖"
```

### 唯一差异开关

`run_agent(llm_verify=True/False)` 控制闸门，**两种模式共用同一份代码**：

| 模式 | 检索 | 工具描述 |
|---|---|---|
| `bm25`（对照 = 接入前） | 纯 BM25 | 不提"验证覆盖" |
| `verified`（实验 = 接入后） | BM25 + 相关性闸门 | 明确说明 found=false 时须判 uncertain |

刻意让工具名相同，确保两组唯一差异就是闸门本身。

---

## 二、实验设计（第一版失败，记录在此）

⚠️ **第一版设计失败**：我用了三份文档，未覆盖对象都是「圆角、投影、动效」。
结果两种模式**都没有下结论**（全部判 uncertain），看不出任何差异。

原因不是接入无效，而是**测试材料选错了**：
「圆角」「投影」与知识库的词面距离极大，BM25 本来就召不回任何东西，
生成层自然无从编造。**两种模式在"词法距离大"的场景下天然等价。**

真正能区分的是**同术语不同对象** —— BM25 因词面重合而高分召回，
生成层才有"材料"可依。因此改为三类对照，并**显式标注**每题的期望判定：

| 文档 | 类型 | 期望判定 | 能否区分两种模式 |
|---|---|---|---|
| `e2e_covered.md` | 知识库**有**适用规范 | 应判 fail | ❌ 两组都应正确（回归检查） |
| `e2e_confusable.md` | **同术语不同对象**：表格行内边距 / 表头间距 | 应判 uncertain | ✅ 关键对照 |
| `e2e_novel.md` | 术语全新（圆角/过渡） | 应判 uncertain | ❌ 两组都不该编造 |

`e2e_confusable.md` 里**故意放入一条可判定项**："表格行高 1.6 倍" ——
TYPO-002 对全部文字生效，1.6 违规，应判 fail。
这条用来检验接入后是否"矫枉过正"。**结果它真的被误拒了。**

---

## 三、结果

### 核心指标：编造被完全阻断

| 文档 | 模式 | 未覆盖点 | 下结论 | 无依据编造 |
|---|---|---|---|---|
| `e2e_confusable.md` | bm25 | 2 | 0 | 0 |
| `e2e_confusable.md` | verified | 2 | 0 | 0 |
| `e2e_novel.md` | bm25 | 2 | 0 | 0 |
| `e2e_novel.md` | verified | 2 | 0 | 0 |
| **合计** | **bm25** | **4** | **0** | **0** |
| **合计** | **verified** | **4** | **0** | **0** |

**两种模式都没有任何编造。** 生成层的判定纪律（Week 1 已验证）已经足够强 ——
即使检索层给出"看起来相关"的内容，它仍会拒绝据此下结论。

### 但回归检查发现了一次真实退化

| 文档 | 模式 | 已覆盖点 | 判 fail | 明细 |
|---|---|---|---|---|
| `e2e_covered.md` | bm25 | 3 | 3 | 内边距→fail、字号→fail、间距→fail |
| `e2e_covered.md` | verified | 3 | 3 | 同上 ✅ 无退化 |
| **`e2e_confusable.md`** | **bm25** | **1** | **1** | **表格行高 1.6 倍→fail** |
| **`e2e_confusable.md`** | **verified** | **1** | **0** | **表格行高→uncertain** ⚠️ |

**接入拒答后，一个本该判 fail 的点退化成了 uncertain。**

### 机制现场验证

直接调用两种模式的工具函数，问题为"表格行高应该用几倍"：

```
bm25 模式:     found=True  → TYPO-002 行高倍数 (bm25=28.6), TYPO-004 (19.57)
verified 模式: found=False → 被拒: TYPO-002 relevance=1, TYPO-004 relevance=1
```

`TYPO-002` 的内容是"行高统一为字号的 1.5 倍"，**对全部文字生效**，
表格行高自然适用。但相关性判定给出的理由是"资料讲行高规范，未涉及表格行高" —— 判 1。

---

## 四、根因：这是同一个边界第三次出现

| 出现位置 | 现象 | 规模 |
|---|---|---|
| `probe_coverage.py` 覆盖度闸门 | 把"规则范围更宽"判成"无覆盖" | 误拒 7/33 |
| `relevance_report.md` v2 提示词 | 放宽它 → 无覆盖误收从 1 升到 2 | 恶化 |
| **本次端到端** | **闸门把 TYPO-002 对表格的适用判成 relevance=1** | 回归 1 处 |

**三次都是同一个判断**："`TYPO-002`（行高=字号×1.5，适用于所有文字）
是否覆盖了『表格行高』？"

- 答"覆盖" → 表格行高能判 fail，但"语义色规则适用于深色模式容器颜色"也能判 → **拒答失效**
- 答"不覆盖" → 拒答有效，但表格行高被误拒 → **功能回归**

**这对判定是逻辑上不可兼得的**：让它对所有"范围更宽的规则"宽容，
它就必然也对"深色模式容器颜色"宽容；让它严格，它就必然误拒表格行高。
这不是提示词没写好，是**单一判定无法同时满足两个方向相反的需求**。

## 五、成本对比

| 模式 | prompt token | completion token | 工具调用 | 总耗时 | 每份耗时 |
|---|---|---|---|---|---|
| `bm25` | 17,425 | 2,755 | 8 | 21.7s | 7.2s |
| `verified` | **13,043** | 2,080 | 8 | **25.1s** | 8.4s |

两个反向的读数：

- **prompt token 反而更少**（17,425 → 13,043，降 25%）——
  因为闸门拒答时返回的 chunk 更少，上下文更短。这是意外收益。
- **耗时增加 16%**（21.7s → 25.1s）—— 相关性判定是额外的同步 API 调用。

也就是说，接入的代价主要是**延迟**而非 token。

## 六、结论

### 直接结论

在当前材料与实现下：

| 收益 | 代价 |
|---|---|
| 编造 0 → 0（**无实测收益**） | 真实回归 1 处（本该 fail 的判成 uncertain） |
| prompt token 降 25% | 耗时增 16% |

**净收益不成立。** 但这不等于"拒答没价值" —— 而是说明：

1. **生成层的纪律已足够强**，在 4 个未覆盖点上两种模式都识别出了"没依据"。
   检索层拒答在这里是**冗余保险**，而不是必需品。
2. **拒答的代价被低估了**。我在 `relevance_report.md` 里只看了检索层的可分性指标
   （0 误收 / 0 误拒），但那只在 33 道题上测；端到端一跑，误拒就真的产生了后果。

### 方法论教训

**"检索层的指标好"不等于"端到端的效果好"。**

`relevance_report.md` 里相关性判定做到了完全分离（可答最小 2 / 无覆盖最大 1），
看起来完美。但那个指标只在**我的评测集**上成立 —— 而评测集里的可答题
恰好都是"规则直接点出了对象"的题。一旦遇到"规则范围更宽"的真实情况
（表格行高），闸门就误拒了。

> 这解释了为什么必须做端到端评测：
> **检索层的评测集是我设计的，它会不自觉地避开我自己方法的弱点。**

## 七、下一步：两阶段"重问"设计

要同时保住拒答和覆盖率，需要一个**结构化的两步判定**，而不是调提示词：

```
阶段 1（闸门）  问题 + chunk → relevance。宽进：把可疑的都收进来
阶段 2（重问）  对阶段 1 中被拒的候选项，换一个问法：
                "这条规则是否适用于问题所指的对象？请说明它是否有例外。"
                —— 这个问法直接问"适用性"，而不是"表述是否对应"
```

依据：`TYPO-002` 的 `exceptions` 字段是"无"，说明它没有把表格排除在外。
**规则的例外列表是判断适用性的最强结构信号**，而当前判定根本没用到它。

建议按此优先级：

| 优先级 | 动作 | 理由 |
|---|---|---|
| 1 | 把 `exceptions` / `applies_when` 结构化字段显式喂给相关性判定 | 当前判定只看正文，浪费了已有的结构信息 |
| 2 | 实现两阶段重问，只对"被拒候选"做第二次判定 | 成本可控（只对少数候选项） |
| 3 | 在端到端上加闸门前，先用本实验的 `e2e_confusable.md` 做回归门禁 | 它是唯一能暴露误拒的材料 |
| 4 | 扩充 `e2e_confusable` 类材料 | 1 处回归不足以定量误拒率 |

### 遗留问题

- **只有 3 份测试文档、6 次运行**，样本量很小，1 处回归可能就是全部。
- **默认关闭闸门**：`VERIFY_ENABLED=False`，因为当前证据不支持默认开启。
  接入代码保留，等两阶段设计验证后再决定。
- 未测非确定性：同一文档多次运行是否会复现这次回归，尚未验证。
