# 实验报告：拒绝原因分类（reject_reason）修复端到端回归

**要解决的问题**：`e2e_report.md` 观察到的回归 ——
**表格行高 1.6 倍**由 `fail` 退化为 `uncertain`。

**结论：修复成功，且未引入新的幻觉。** 3/3 预注册判据全部通过。

复现：`python -m eval.probe_reject_reason`

---

## 一、根因回顾（来自 `structured_report.md`）

回归的真实原因**不是检索层误拒** —— 相关性判定（v1）本来就把 `TYPO-002`
以 relevance=3 传给了生成层。问题在**工具 schema 的措辞**：

> "若返回 **found=false**，说明知识库没有覆盖该对象的规范，
> 此时**必须判 uncertain**并把 evidence 留空"

这个措辞把 `found=false` 这一个布尔值等同于"无法判定"，
但 `found=false` 实际上混合了两种语义完全相反的情况：

| 情况 | 语义 | 生成层应做什么 |
|---|---|---|
| 规则**明确排除**该对象 | 该对象不受约束 → **本身就是一个结论** | 判 pass |
| 知识库**无覆盖**该对象 | 确实无法判定 | 判 uncertain |

**一个布尔值承载不了这个区分。** 所以修复方向不是调判定器，而是
**把"为什么被拒"作为结构化字段传下去**。

---

## 二、实现：独立的第二道判定

### 拒绝原因分类器

新增 `classify_rejection()`，对"全被拒"的情况单独判定原因：

| reason | 含义 | 生成层行为 |
|---|---|---|
| `excluded` | 例外条款明确点出该对象 | 该对象不受约束 → **判 pass** |
| `not_applicable` | 规则讲的是另一个对象 | 判 uncertain |
| `no_coverage` | 只沾到主题边缘 / 无关 | 判 uncertain |

### 为什么原因判定必须是独立的一道

`structured_report.md` 已经证明：**同一个语言模式「被明确排除」对应两种相反解读**——
"规则不约束它"（已给答案）vs "规则没提它"（无法回答）。
用相关性分数的高低去推断原因，必然混淆这两者。

所以原因判定用**另一个提示词**、另一个输出维度，不复用相关性打分。

### 工具措辞同步修正

原来只说"found=false → uncertain"，现在明确分三种情况：

```
1) found=true                        → 有适用规范，据此判定
2) found=false + excluded            → 该对象被明确排除，是有效结论，判 pass
3) found=false + no_coverage         → 判 uncertain，evidence 留空
                / not_applicable
```

## 四、一条完整的因果链

这个修复之所以能定位，依赖前面四份报告的接力：

| 报告 | 贡献 |
|---|---|
| `retrieval_report.md` | 发现 BM25 无法拒答（信号方向还是反的） |
| `relevance_report.md` | 证明 LLM 相关性判定可以拒答；记录运行间波动 |
| `e2e_report.md` | 端到端跑出回归（但根因判断错了） |
| `structured_report.md` | **纠正根因**：不是检索层误拒，是工具措辞把布尔值当成了语义 |
| **本报告** | 用结构化的拒绝原因修复，预注册判据全部通过 |

**关键转折点**是 `structured_report.md` 那次"结论被自己推翻"。
如果当时接受了"逻辑上不可兼得"的判断，就不会有 `reject_reason` 这条路 ——
而实际上问题根本不在判定逻辑的边界上，在**信息传递的形式**上。

> 这个教训值得单独记住：
> **当两个需求"逻辑上不可兼得"时，首先要怀疑的不是需求，是它们共用的那个表达形式。**
> `found` 这一个布尔值就是那个表达形式 —— 换成三值枚举，矛盾就消失了。

## 五、当前状态与下一步

### 已具备的能力

```
检索层：BM25 粗排 → LLM 相关性闸门 → 拒绝原因分类（excluded / not_applicable / no_coverage）

```

两层形成一致的降级链路，且**每种降级都带有可解释的原因**。

- 拒绝原因分类是**额外一次 API 调用**（每题 1 次），成本在相关性判定的基础上再增加。
- 本次未重复运行，未测运行间波动对 `reject_reason` 的影响。
- 观察到 `表格行高 1.6 倍` 判 `pass` 时 evidence 为空 —— 这是符合设计的
  （排除型结论没有规范原文可引），但下游若用"evidence 为空 = 可疑"做校验会误判。
  **这个语义差异需要写进 README，否则后续维护者会困惑。**
