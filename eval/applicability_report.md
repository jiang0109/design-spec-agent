# 实验报告：适用性结构化（优先级 2）

**任务**：修掉生成层剩余 3 处「过度拒答」—— 规则就在眼前，却被判定器判为不适用。

**结论：诊断反转了。真正的缺陷不是"适用性判断"，而是 agent 的"查询表述"。**
KB 修好 1 处确定性缺陷，v3 判据测试后**不启用**，同时发现一个更根本的问题：
**聚合准确率稳定在 96%，但错误的组成逐次变化。**

复现：`python -m eval.probe_applicability`

---

## 一、诊断反转：去查"agent 到底问了什么"

最初我以为判定器太严格 —— 它在拿"标题是否提到对象"当判据。
但把评测记录里 **agent 实际发出的查询语句**拉出来后，情况完全不同：

| 案例 | agent 实际问的是 | 规则实际管的是 |
|---|---|---|
| E016 | 按钮高度**允许哪几档取值** | SPACING-005 管的是**高度下限 ≥40**，不是档位 |
| E024 | 分隔线颜色引用**应使用哪个色阶变量** | COLOR-003 恰恰**禁止**用色阶变量 |
| E060 | 图层名称**是否必须与内容一致** | NAME-003 管的是**默认名称**，不管一致性 |

**三个问题都预设了知识库不支持的框架。判定器拒得对。**

E024 最能说明问题：问题假设"应该用某个色阶变量"，而规则说的正是"不该用"。
从产品角度规则**回答了**它（"你不该用色阶变量"），所以值得接受；
但 E060 那类（问"名称与内容是否一致"）知识库根本没有任何规则涉及，**无解**。

> 这是本项目第七次「先诊断、后动手」救回一轮工作。
> 如果直接去改判定器提示词，就会在错误方向上做第四次迭代
> （`relevance_report.md` 已经有过三轮失败的提示词迭代）。

## 二、确认并修复一个真实的 KB 缺陷

三条例子里，只有 `SPACING-005` 是 KB 本身有问题：

```yaml
# 修复前
applies_when:
  - 组件由两个及以上内部元素构成     # 只覆盖了「间距」这个方面

# statement 却管两件事：
#   ① 内部元素间距取值为 4 的整数倍
#   ② 且任一可点击元素的高度不低于 40   ← applies_when 没有覆盖

# 修复后
applies_when:
  - 组件由两个及以上内部元素构成（用于判定内部元素间距取值）
  - 评估可点击元素的高度时（按钮、图标按钮、可点击行等）
```

**效果是确定性的**：`probe_applicability` 里 E016 的相关性从 1 升到 **2**（仅靠 KB 修复，不改判定器）。

## 三、v3 判据（aspect 覆盖）测试结果：**不启用**

我实现了第三版判定提示词，判据从"标题是否提到对象"改成
"规则的约束是否作用在问题所问的属性上"，并显式给出 `适用 / 例外 / 规则原文`。

16 条查询对照 v1 与 v3：

| 组 | 结果 |
|---|---|
| **targets**（应接受） | E016 ✅（v1 已因 KB 修复通过）、E024 ✅（v3 修好 1→3）、E060 ❌（查询问偏，两者都救不了） |
| **allowlist**（正常路径） | 3/3 ✅ 无回归 |
| **reject**（应拒绝） | 8/10 —— **G34 表头间距 1→3（误收）**、**Q30 表格内边距 2→3（更漏）** |

**净效果：修 1 处误拒、坏 2 处拒答。**

病因是"aspect 覆盖"这个判据本身容易把「术语重叠但对象不同」也放进来 ——
问"表头间距"，规则讲"组件内部元素间距"，都属于"间距"这个 aspect，就误放了。
**这是判据的天花板，不是提示词没写细。** 代码保留，但默认版本仍是 v1。

### 顺带发现：v1 本来就有漏

Q30「数据表格的行内边距可以用 8px 吗」在 **v1 下就判 2**（漏）。
说明当前 17/17 的无覆盖战绩，有一部分靠的是**评测集里那道题的措辞恰好绕开了**。
这再次印证：评测集会不自觉地避开方法的弱点。

## 四、全量重跑：聚合稳定，但错误组成不稳定

KB 修复后重跑 120 点（v1 判据）：

| 指标 | v3（修复前） | v4（KB 修复后） |
|---|---|---|
| 端到端准确率 | 96%（115/120） | **96%（115/120）** |
| 误报 FP | 0 | 0 |
| 过度拒答 | 3 | **0** |
| 过度自信 | 0 | **2** |
| 漏报 | 2 | **3** |

**但错误的具体位置几乎全变了：**

```
v3 的 5 处错误： E009  E016  E024  E043  E060
v4 的 5 处错误： E009  E043  G34   E053  E078
重叠只有 2 个（E009、E043）
```

只有 E016 的修复可以归因于 KB 改动（探针已确定性验证）。
**E024、E060 在 v4 里"通过"更像是查询表述碰巧变好了**，而不是被修好了。

> 这是本轮最重要的发现：**96% 这个聚合数字是稳定的，但它由哪 5 个错误构成是不稳定的。**
> 原因是 agent 每次会**动态生成不同的查询语句**，而适用性判定高度依赖查询措辞。
>
> 这意味着：**单看准确率会掩盖一个系统性缺陷** —— 判定结果不可复现。

### 另外发现一例重复用例

`G34`（"表头与首行间距 12px"）与 `E078`（"表头间距使用 12px"）是**同一个场景**，
却在 v4 里同时失败、被计为 2 个错误。评测集应去重，否则会**放大单一缺陷的权重**。

### 修正后的下一步优先级

| 顺序 | 动作 | 依据 |
|---|---|---|
| **1** | **约束 agent 的查询表述** | 三个误拒里两个源于查询问偏（E024 预设错、E060 臆造维度）；约束查询格式能同时改善适用性与可复现性 |
| **2** | 规则引擎接管判定步骤（原优先级 2） | 修 E009 / E043 / E053 这类"算错"与"漏项"，且覆盖 75% 判定点 |
| 3 | 评测集去重（G34/E078） | 现在单一缺陷被计两次，高估了影响面 |
| 4 | 多次重复评测，报告错误组成而非只报准确率 | 聚合稳定掩盖了组成不稳定 |

### 对"约束查询表述"的具体设想（未验证）

当前 agent 自由生成查询，会出现"应使用哪个色阶变量""是否必须与内容一致"这类
**知识库不存在的判断维度**。可以在工具描述里规定查询格式：

```
查询 = 对象 + 属性 + 取值
例： "卡片内边距 20px"、"图层名 Rectangle 45"、"按钮高度 32px"
禁止： 引入规范未定义的判断维度（如"是否与内容一致"）
```

这是低风险、可测的改动，但**必须用完整 120 点评测验证**（本轮已多次证明：
局部修好可能带来另一侧的回归）。
