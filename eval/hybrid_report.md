## 一、架构

```
文档陈述
   │
   ▼
① 抽取（LLM）      自然语言 → {statement, attribute, claim}
   │               attribute 必须取自**受控词表**
   ▼
② 路由（查表）     attribute → rule_id + claim 规整
   │               文字对比度按字号/字重分流 COLOR-001 / COLOR-002
   ▼
③ 判定
   ├─ 属性在闭集内 + 引擎支持 → 规则引擎（确定性、可复现、可单测）
   └─ 属性 unknown 或引擎不支持 → 回落（标记为需 LLM / 语义层）
```

### 为什么用受控属性词表，而不是自由文本匹配

前几轮已经反复证明：让判定器判断"这条规则是否适用于这个对象"，
在措辞变化下极不稳 ——

| 尝试 | 结果 |
|---|---|
| `relevance_report.md` 三版提示词 | 无法稳定解决 |
| `applicability_report.md` v3 aspect 判据 | 修 1 处、坏 2 处 |
| `query_phrasing_report.md` 措辞调优 | 到尽头 |

**如果属性名来自一个闭集，"属性 → 规则"就是查表，不需要语义判断。**
代价是抽取器必须在闭集里选 —— 这正是 LLM 擅长的（分类），
而"是否适用"这个需要精确判断的事被彻底绕开了。

### 为什么不做"引擎判定 + LLM 复核"

复核会把不确定性重新引回来，而这一整轮改动的目的就是消除它。
对确定性结论做二次语义判断，等于让模型有机会否决算术结果。

当前唯一允许的回落是**结构性失败**：属性不在闭集，或 claim 形状与规则约束不匹配
（抽取没给全字段）。这两种情况下引擎输出 `uncertain` 并标注 `source=fallback`，
由上层决定走 LLM 路径。

## 二、受控属性词表

23 个属性 → 22 条规则：

| 属性 | 规则 | claim 字段 |
|---|---|---|
| 卡片内边距 / 卡片间距 / 页面外边距 | SPACING-001 / 002 / 004 | `{"value": 数值}` |
| 分组间距 | SPACING-003 | `{"inside": 组内, "between": 组间}` |

| 字号 / 字重 / 正文默认字号 | TYPO-001 / 003 / 004 | `{"value": 数值}` |
| 行高 | TYPO-002 | `{"size": 字号, "line_height": 行高}` |
| 属性声明 | COMP-001 | `{"declared": [...]}` |
| 属性命名 / 布尔属性命名 | COMP-002 / 003 | `{"name": "属性名"}` |

这就是"知识库未覆盖就诚实说不知道"在架构上的落点。

## 四、唯一失败项：E005 是我的 fixture 有问题

E005 的文档（我早前把它改成）：

> 分组内容区 · 卡片间距：不同分组之间的间距为 24px。

抽取器把它路由到 **分组间距（SPACING-003，关系式）**，
但文档**只给了组间值，没给组内值** —— 关系式无法求值，
引擎输出"claim 形状不匹配"并回落。

两个层面都有问题，且都值得记：

1. **路由歧义**：「不同分组之间的间距」既可以归 `卡片间距`（SPACING-002，允许 16/24），
   也可以归 `分组间距`（SPACING-003，关系式）。当前词表没有区分这两者的语用差别。
2. **fixture 欠定义**：我自己在上一轮把 E005 从「组内 16 / 组间 24」简化成
   「不同分组之间的间距为 24px」来消除另一个歧义，结果造出了新的欠定义。

**引擎的行为是对的** —— 信息不足就不猜，回落到需要语义的路径。

## 五、已知限制（接入 agent 前必须处理）

| 限制 | 影响 | 应对 |
|---|---|---|
**排除型（excluded）会回落** | 表格行高、全屏卡片内边距这类"规则明确排除"的案例，引擎不做例外判断，会输出 uncertain | 必须让 LLM 分支与之并存（**不是替换**），由上层合并两条路径的结果 |
| 未接入 agent 主流程 | CLI / `run_agent` 仍走 `search_spec_verified` → LLM 判定 | 尚未做，需要一次全量验证 |

| 抽取层未做稳定性测试 | 单次运行，未重复 | 抽取（temperature=0）是否稳定未知 |
| 生成器文档有重复前缀 | 形如「内边距：内边距内边距使用 12px」 | `gen_generation_set.py` 模板 `"{label}：{label}{text}"` 里 text 已含 label。属 cosmetic，改动会波及已发布的评测数字，故暂不动 |

## 六、判断：这是一条正确的分工，不是替换

本轮最重要的认识不是"9/10"，而是把职责切清楚了：

| 层 | 谁做 | 为什么 |
|---|---|---|
| 把自然语言变成结构化 claim | **LLM** | 这是分类/抽取，模型擅长且容错高 |
| 判断 claim 是否满足约束 | **代码** | 这是算术/集合/正则，模型**会算错**（E009/E013/E043 为证） |
| 处理知识库未覆盖的对象 | **LLM + 语义** | 需要理解"规则讲的是不是这件事"，代码做不到 |
| 写理由与建议 | **LLM** | 表达 |

`decidability_report.md` 的数字在这里得到印证：
**可确定性的 75% 出全部错误，需语义的 25% 零错误。**
分工方案正是把前者交给代码、后者留给模型。
