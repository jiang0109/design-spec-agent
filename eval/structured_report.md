# 实验报告：把「例外」结构字段喂给判定器

**要检验的命题**（来自 `e2e_report.md` 四、）：

> 「规则范围更宽」这个边界**逻辑上不可兼得** ——
> 要么宽容（拒答失效），要么严格（误拒表格行高）。

我当时给出的依据是：`TYPO-002` 的例外写着"表格单元格不参与行高倍数校验"，
而判定器看不到它。**这个依据是错的** —— 本实验推翻了自己上一份报告的结论。

复现：`python -m eval.probe_structured`（真实 API 调用）

---

## 一、先修了一个真实的架构缺陷

早期 `chunk_heading_split` 为了省字符，把结构化参数**只挂在每个 Section 的第一个子块**上。
实测后果：

| | chunk 数 | 含「例外:」 |
|---|---|---|
| 修复前 | 72 | **23（32%）** |
| 修复后（`repeat_params=True`） | 72 | **48（66%）** |

**49 个 chunk 完全看不到例外条款。** 判定器只看到被召回的 chunk，
所以"例外不可见"这个风险是真实存在的 —— 虽然下面的实验证明它不是本次回归的原因，
但这个修复本身是对的（省下的字符不值得让关键约束可能不可见）。

---

## 二、决定性发现：判定器**早就看到并理解了例外**

探针 P1「表格单元格的行高用 1.6 倍可以吗」，gold = `TYPO-002`：

```
TYPO-002  bm25=53.8  v1=3  v2=1  ←gold
   v1理由: 资料明确表格单元格不参与行高倍数校验，可用1.6倍
   v2理由: 表格单元格被明确列入例外，不参与行高倍数校验
```

**v1（只看正文）就已经读到并正确理解了例外条款**，而且据此给出 relevance = **3**，
把正确的 gold 内容传给了生成层。

也就是说：**检索层从未误拒"表格行高"。** `e2e_report.md` 里那段
"TYPO-002 relevance=1 被拒"的现场验证，捕获到的是**另一次运行**的结果
（相关性判定存在运行间波动，我在 `relevance_report.md` 里已记录过这个现象）。

### 那端到端回归到底是怎么来的？

检查当时生效的工具 schema 措辞：

> "若返回 **found=false**，说明知识库没有覆盖该对象的规范，
> 此时必须判 uncertain 并把 evidence 留空"

问题在生成层对 `found=false` 的**过度服从**：
只要闸门没放行，它就倾向于判 uncertain，而不去分辨
"没放行是因为规则不适用"还是"没放行是因为对象无覆盖"。

**所以那不是"检索层误拒"造成的回归，而是我的工具措辞把"found=false"这一个信号
错误地等同于"必须判 uncertain"。**

## 三、v2 的实测结果：更差

既然例外字段早已可见，那"显式喂给它 + 规定三步判定顺序"能否带来改善？

全量评测集（33 可答 + 2 无覆盖，每题 top-5）：

| 版本 | 可答均值 | 可答最小 | 无覆盖最大 | 误拒（可答<2） | 误收（无覆盖≥2） |
|---|---|---|---|---|---|
| **v1 只看正文** | 2.97 | 2 | 2 | **0/33** | 1/2 |
| v2 含适用/例外 | 2.94 | **1** | 2 | **1/33** | 1/2 |

**误拒：0 → 1（变差）；误收：1 → 1（无改善）。**

### 为什么更差：同一个语言模式，两种相反的解读

v2 的判定规则是"如果问题对象出现在例外列表里 → 该规则**明确不适用** → 判 1"。
这条规则在 P1 上被严格执行了，但**语义上并不正确**：

> `TYPO-002` 的例外说"表格单元格不参与行高倍数校验"。
> 这句话的含义是"**这条规则不约束表格**"，而"不约束"意味着
> **不存在违规** —— 它回答了问题，而不是回避了问题。

于是同一个字面模式「被明确排除」对应两种相反的判定：

| 场景 | 字面 | 正确解读 | 应给分 |
|---|---|---|---|
| 「表格单元格不参与行高校验」 | 被排除 | 规则不约束该对象 → **已给出答案**（无违规） | 高 |
| 「深色模式下容器的颜色值」 | 未被提及 | 无规则覆盖该对象 → **无法回答** | 低 |

**两者都表现为"规则与问题对象不匹配"，但一个是"已覆盖且不约束"，另一个是"未覆盖"。**
v2 把两者一律压成低分，所以矫枉过正。

**这不是提示词没写好 —— 是这个判定维度本身无法用「匹配/不匹配」来表达。**

---

## 四、推翻上一份报告的核心结论

`e2e_report.md` 四、的结论是"该边界**逻辑上不可兼得**"。**这个结论下早了。**

修正后的结论：

1. **判定器本来就具备理解例外的能力**（P1 的 v1 理由为证），
   所以"逻辑上不可兼得"的前提不成立。
2. 端到端那次回归的真实原因是**工具 schema 的措辞**——把 `found=false`
   单一信号等同于"必须判 uncertain"，让生成层无法区分
   "规则不适用"与"对象无覆盖"。
3. **架构缺陷（例外只挂第一个子块）是真实存在的**，但与本回归无关，
   属于需要修的隐患。

> 这是本项目第五次"结论被自己的验证推翻"：
> Week 1 指标字段名写错 → pilot 选错口径 → 粒度实验浮点阈值判错 →
> 拒答实验三轮改提示词（根因在评测集坏题）→ **本次：结论建立在未验证的前提上。**
>
> 共同点仍然是：**错误的来源都在"如何度量与解释"这一层，
> 而不在业务逻辑里。** 每一次都靠逐题/逐块检查发现。

## 五、下一步：修工具措辞，而不是修判定器

既然根因在工具 schema 的措辞，正确的修复方向是**让检索结果携带"为什么被拒"**：

```
当前（有缺陷）  found=false                        → 生成层只能猜，倾向一律 uncertain
改进方向        found=false + reject_reason 字段：
                  "no_coverage"   对象完全无规则   → 应判 uncertain
                  "excluded"      规则明确排除该对象 → 该对象不受约束，可判 pass
                  "not_applicable" 规则讲的是别的对象 → 应判 uncertain
```

这样生成层不必从单一布尔值推断语义，而是拿到**结构化的拒绝原因**。
而 `exceptions` 字段正是产出 `rejected_reason` 的依据 —— 所以本实验的
架构修复（让例外在每个子块可见）是这条路径的前提。

### 优先级

| 优先级 | 动作 | 理由 |
|---|---|---|
| 1 | 给 `search_spec_verified` 增加 `reject_reason` 字段（no_coverage / excluded / not_applicable） | 直击端到端回归的真实根因 |
| 2 | 保持判定器为 **v1**（v2 实测更差，不要采用） | 用数据决策，不用直觉 |
| 3 | 保留 `repeat_params=True` 的架构修复 | 是 reject_reason 的前提 |
| 4 | 用 `e2e_confusable.md` + P1 做回归门禁 | 唯一能暴露此类问题的材料 |

### 遗留问题

- **v1 与 v2 的差异只有 1 题**（误拒 0 vs 1），样本量不足以给出强结论。
  "v2 更差"的证据强度有限，但"v2 没有更好"是清楚的。
- 本次只跑了 1 遍全量，未做多次重复。相关性判定的运行间波动
  （`relevance_report.md` 已记录，差距在 1.76~1.97 档之间摆动）
  意味着这些边界数字随时可能翻转。
- `e2e_report.md` 中"逻辑上不可兼得"的表述已被本报告推翻，
  但原报告保留原样，以便追溯结论的演进过程。
