# 规则引擎：把确定性判定从 LLM 手里拿回来

**目标**：`decidability_report.md` 算出 75% 的判定步骤可用代码执行，
且当前所有错误都落在这 75% 里；`query_phrasing_report.md` 进一步查明这些错误的
共同点是「**规则已召回、约束已读到，但判定器不采用它**」。
所以把判定步骤交给代码执行。

**结论：引擎覆盖 22/23 条规则，37 个离线断言全部通过，
并且把 3 个 LLM 判错的真实案例全部判对了。**

复现：`python -m eval.test_rule_engine`（**完全离线，零 API 调用**）

---

## 一、职责边界（这个划分是整个方案的前提）

```
抽取   自然语言文档 → {"attribute": "内边距", "claim": {"value": 32}}
       ← 仍由 LLM 完成，本模块不解决

判定   claim → 合规/违规 + 命中的字段与期望值
       ← 本模块负责：纯函数、无网络、确定性

表达   判定结果 → 理由与修改建议
       ← 交给 LLM
```

**规则引擎不解决抽取**。真实落地时从「内边距使用 32px」里正确抽出 `32`
才是主要工作量；引擎只是在抽取之后接管"要不要算、怎么算"这一步。

---

## 二、实现：从知识库编译出可执行约束

引擎直接读 `kb/` 的 front-matter，把 `params` 编译成判定逻辑。
支持的约束类型与对应规则：

| 约束 | 含义 | 覆盖的规则 |
|---|---|---|
| `allowed` | 取值白名单 | SPACING-001/002/005、TYPO-001/003、COMP-005、COLOR-004 |
| `step` | 必须是某数的整数倍 | SPACING-005 |
| `min` / `min_touch_target` | 下限 | COLOR-001/002、SPACING-005 |
| `max_content_width` | 上限 | SPACING-004 |
| `range` | 区间 | SPACING-004 |
| `multiplier` | 倍数（行高 = 字号 × 1.5） | TYPO-002 |
| `constraint` | 关系式（between > inside） | SPACING-003 |
| `pattern` | 正则（要求形式） | COMP-002/003、NAME-001/002/004 |
| `pattern` + `forbidden_examples` | 正则（禁止形式） | NAME-003 |
| `required_pattern` / `forbidden_pattern` | 语义 token 校验 | COLOR-003 |
| `required` | 必须声明的项 | COMP-001 |
| `default` | 默认值必须等于规定值 | TYPO-004 |
| `defaults`（按规则识别） | 必须有默认值 | COMP-004 |

**覆盖率 22/23**。唯一不支持的是 `COLOR-005`（状态色是否被误用）——
它本质上需要判断"这个颜色用在这个场景算不算状态语义"，属于语义判断，
**应当留给 LLM**（与 `decidability_report.md` 的分类一致）。

---

## 三、验证：37 个离线断言

`eval/test_rule_engine.py` 用断言覆盖每一种约束类型，并**专门收录
3 个 LLM 判错的真实案例**作为回归用例：

| 案例 | LLM 判定 | 引擎判定 | 依据 |
|---|---|---|---|
| **E009** 组内 24 / 组间 24 | pass ❌ | **fail** ✅ | 组间必须**严格大于**组内 |
| **E013** 内容区最大宽度 1440 | uncertain ❌ | **fail** ✅ | 超过 `max_content_width: 1200` |
| **E043** 正文默认字号 12px | pass ❌ | **fail** ✅ | 默认值必须等于 14 |

这三条正是"把可计算的事交给模型去猜"造成的错误。现在它们是引擎的回归用例：
**任何人改动解析逻辑，只要让这三条回退，测试立刻失败。**

跑通结果：**37/37 通过**，并已接入冒烟测试（`test_smoke` 第 10 项），
成为提交前的常规门禁。

## 四、实现过程中发现的 4 个真 bug

全部是**我自己的实现缺陷**，全部由断言暴露（不是"测试写错"）：

| bug | 现象 | 根因 |
|---|---|---|
| 关系式取不到值 | SPACING-003「组内=组间」被判 pass | 规则用 `between_groups`/`inside_group`，claim 用 `between`/`inside`，名字不匹配 → 关系式静默跳过，被 `min_between_groups` 抢先判 pass |
| 上限吃错字段 | SPACING-004「外边距 12」被判 pass | `max_content_width` 用了通用 `value`，把"页面外边距"当"内容宽度"比了 |
| YAML 反转义缺失 | `Button/Primary/Disabled` 被判不合规 | 正则里的 `\/` 从双引号 YAML 读出应反转义成 `/`，没处理就变成"要求反斜杠+斜杠" |
| pattern 方向 | `Rectangle 45` 被判 pass | 多数规则 `pattern` 是**要求形式**（匹配=合规），但 NAME-003 的 `pattern` 是**禁止形式**（匹配=违规），方向反了 |

> 第 4 个尤其值得记：**同一个字段 `pattern` 在不同规则里语义相反。**
> 用 `forbidden_examples` 字段作方向信号（它是"这类写法不允许"的明示），
> 而不是按规则 id 硬编码。

## 五、这套东西的真正价值：可复现

多份报告记录过同一个问题：**判定结果不可复现**。
同一份输入，两次运行可能给出不同判定（`generation_report.md`、
`applicability_report.md` 都有记录，`G32`/`E078` 是实例）。

规则引擎消掉的是这一整类不确定性：

```
同输入 → 同输出
可被单元测试锁定
不随模型版本、温度、供应商变化
出错时可定位到具体字段（field_name / expected / actual）
```

`Result` 里带 `field_name` / `expected` / `actual`，也让"为什么判违规"
变成可解释的 —— 而不是让模型编一个理由。

## 六、还没做：接入 agent

这是本轮明确**没做**的部分，需要说清楚：

| 缺什么 | 说明 |
|---|---|
| claim 抽取器 | 需要一个 LLM 步骤把文档陈述转成 `{attribute, claim}` |
| 工具接线 | 现在 agent 仍然调 `search_spec_verified` → LLM 判定；未改为"先查引擎" |
| attribute → rule 映射 | 引擎按 `rule_id` 判定，但"这个陈述该用哪条规则"仍是难题（就是那个适用性边界） |
| 端到端验证 | 未跑 120 点全量评测 |

### 关于"用哪条规则"

这是接入时最关键的设计问题，也**不能靠 prompt 解决**（已试过三次）。
可选路径：

1. **属性词表**：把 `id, title, applies_when` 编译成"属性 → 规则"的反向索引，
   由抽取层直接产出受控词表里的属性名，避免自由文本匹配
2. **先召回再筛选**：用 BM25 召回候选规则集，引擎只对候选执行判定，
   LLM 只在候选为空或全部不可执行时介入
3. **保留闸门但降级**：引擎能判的走引擎，引擎说"不匹配 claim 形状"时回落到 LLM

推荐路径 1 + 3 组合，但**必须先做一次全量评测确认没有回归**。

### 遗留风险

- 测试只覆盖 37 个断言、6 条规则以外多数规则各 1-2 条，**未穷举边界**
  （如负数、浮点、多值同时违规的优先级）。
- 引擎按 `rule_id` 判定，**假定"用哪条规则"已被正确确定** ——
  而这一步仍是开放的。
- `params` 解析是手写的极简 YAML，**遇到新写法可能静默解析失败**。
  建议后续在 `validate_kb` 里加一条校验：每条规则至少有一个引擎可识别的约束字段。
