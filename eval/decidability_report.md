# 分析报告：判定步骤的可确定性化程度

**问题**：120 个判定点里，有多少的"判定步骤"可以交给确定性代码执行？
这个数字决定"规则引擎 + LLM 混合架构"值不值得做。

**结论：90/120 = 75% 的判定步骤可确定性化。**
但更重要的是一个**反直觉读数**：错误 100% 落在可确定性的那 75% 里，
而需要语义判断的 25% 是零错误。

复现：`python -m eval.probe_decidability`

---

## 一、必须先讲清的口径

"规则可确定性判定" ≠ "整条链路可确定性判定"：

| 环节 | 能否确定性化 | 说明 |
|---|---|---|
| **抽取**：自然语言 → 具体取值 | ❌ 仍需 LLM / 正则 | 文档是「内边距使用 32px」这样的自然语言 |
| **判定**：取值 → 合规/违规 | ✅ 对有硬参数的规则可纯代码执行 | 本报告关心的部分 |

所以本报告统计的"可确定性"**只指判定步骤**。它直接回答"哪类错误会结构性消失"。

分类依据是规则 `params` 里有没有可直接执行的约束（我在脚本里按规则逐条归类，
不是机器自动判定的，可复核、也可质疑）：

| 桶 | 含义 | 典型规则 |
|---|---|---|
| `enum` | 取值白名单比对 | SPACING-001 `allowed [12,16,24]` |
| `numeric` | 阈值 / 区间比对 | COLOR-001 `contrast ≥ 4.5` |
| `formula` | 倍数或关系式 | TYPO-002 `multiplier 1.5`、SPACING-003 `between > inside` |
| `format` | 正则 / 命名格式 | COMP-002 camelCase、NAME-002 PascalCase |
| `presence` | 声明与默认值的存在性 | COMP-001 必须声明 size 与 variant |
| `coverage` | 覆盖度判断 | 无覆盖 / 排除型 —— **需语义** |
| `judgment` | 其余语义判断 | COLOR-005 状态色是否误用 —— **需语义** |

---

## 二、结果

| 桶 | 点数 | 占比 | 归类 |
|---|---|---|---|
| enum | 27 | 22% | 可确定性 |
| numeric | 17 | 14% | 可确定性 |
| formula | 13 | 11% | 可确定性 |
| format | 25 | 21% | 可确定性 |
| presence | 8 | 7% | 可确定性 |
| **可确定性合计** | **90** | **75%** | |
| coverage | 27 | 22% | 需语义 |
| judgment | 3 | 2% | 需语义 |
| **需语义合计** | **30** | **25%** | |

### 反直觉发现：错误全在"能算"的那一侧

| 桶 | 点数 | 错误 | 错误率 |
|---|---|---|---|
| enum | 27 | 0 | **0%** |
| numeric | 17 | 1 | 6% |
| formula | 13 | 2 | **15%** |
| format | 25 | 2 | 8% |
| presence | 8 | 0 | **0%** |
| **可确定性合计** | **90** | **5** | **6%** |
| coverage | 27 | 0 | **0%** |
| judgment | 3 | 0 | **0%** |
| **需语义合计** | **30** | **0** | **0%** |

**让模型去算它本来可以算的事，错误率 6%；让它做需要语义的事，错误率 0%。**

这和我们通常的直觉相反（"LLM 不擅长精确计算"是对的，但更精确的说法是
**"我们不该让它做精确计算"**）。而且它给出了明确的架构方向：
**该由代码做的部分交给代码，模型专做语义。**

---

## 三、5 处错误：需要的其实不是同一件事

把"判定步骤换成代码"听起来能修掉全部 5 处，但实际上分两类：

| 案例 | 桶 | 错误 | 真正需要什么 |
|---|---|---|---|
| E009 组内24/组间24 | formula | 漏报 | 取值抽取 + **确定性判定执行** |
| E043 正文默认字号12px | numeric | 漏报 | 取值抽取 + **确定性判定执行** |
| E016 按钮高度32px | formula | 过度拒答 | **适用性映射**（规则管不管这个对象） |
| E024 分隔线 gray-300 | format | 过度拒答 | **适用性映射** |
| E060 Rectangle 45 | format | 过度拒答 | **适用性映射** |

- **前 2 处**：规则引擎能直接修好。它们都是"取值比对算错"——
  组间要严格大于组内、默认字号必须等于 14，这些是纯计算。
- **后 3 处**：规则引擎修不掉。它们的错误在于**判定器认为规则不适用**，
  属于"适用性判断"，需要的是**结构化的适用范围映射**，不是计算能力。

> 这一区分很重要：如果我只报"5/5 都能结构性修好"，就夸大其词了。
> 实际是 **2/5 靠规则引擎、3/5 靠适用性结构化**，两个不同的工程动作。

## 四、这个数字的可信度

### 支持

- 120 个判定点，覆盖 23 条规则全量，分桶按规则的 `params` 逐条归类。
- 错误位置是**顺序对齐**评测结果得到的，不是靠字符串猜测
  （第一版用 target 匹配，因为桶里的点没有 target 字段，错误率恒为 0 —— 假绿，已修）。

### 限制

- **分桶是我的判断，不是机器测量的**。比如把 COLOR-003 归为 `format`（语义 token
  与原始色值在**模式**上可判别）是可争议的 —— 现实里"什么算语义 token"仍有边界。
- **抽取环节完全不在这 75% 里**。真实落地时，从「内边距使用 32px」里正确抽出
  `32` 才是主要工作量；规则引擎只是在抽取之后接管判定。
- **只用 120 个判定点**。样本小，6% 与 0% 的差异在统计上并不强
  （5/90 vs 0/30，Fisher 精确检验也不显著）。**方向可信，强度不可夸。**

## 五、修正后的优先级

| 顺序 | 动作 | 依据 |
|---|---|---|
| **1** | **适用性结构化**（修 E016/E024/E060 那类） | 3/5 错误；且它同时决定幻觉与误拒两端 |
| **2** | **规则引擎接管判定步骤**（修 E009/E043 那类） | 2/5 错误；覆盖 75% 判定点，消除算错类波动 |
| ~~3~~ | ~~提升 BM25 排序质量~~ | 当前 5 处错误里收益为 0，**不做** |
| 4 | LangGraph + checkpointer | 面试考点，属"补框架" |

### 一个反建议：不要为了"覆盖率"去硬做 coverage 判定

`coverage` 占 22%（27 点），且**当前 100% 正确**。它的本质是"知识库有没有覆盖这个对象"，
天然需要语义理解 —— 试图把它做成规则引擎是过度工程。
**这 22% 就该留给模型，而且它现在做得很好。**

## 六、如果要做规则引擎，最小可行形态

```
LLM 抽取        从自然语言文档里抽出结构化声明
                  {对象: "卡片内边距", 属性: "padding", 值: 32, 单位: px}
       ↓
代码判定        按规则 params 执行，输出 合规/违规 + 命中的规则与字段
                  SPACING-001: allowed=[12,16,24], 32 ∉ allowed → fail
       ↓
LLM 组织        把确定性结论写成自然语言理由与修改建议
```

关键收益不是"更准"，而是**可解释与可回归**：
判定结果可以被单元测试覆盖，不随模型版本或温度漂移。
今天的评测里已经出现过同一输入两次不同判定（G32/E078），规则引擎能消除这一整类不确定性。
