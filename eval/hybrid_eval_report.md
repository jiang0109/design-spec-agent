## 一、演进过程：每次修的都不同

### v1 → v2：例外粗筛（87% → 92%）

v1 的引擎**完全忽略 `exceptions`**，于是「全屏沉浸式视图内的卡片内边距 8px」
被判 `fail`（8 不在白名单），而正确答案是 `pass`。
排除型一组从 LLM 路径的 10/10 掉到 2/10。

修法：判定前先用中文 3-gram 判断陈述是否落在例外里，命中就交回 LLM。

> 这里我先做了一个**错误的预测**：以为排除型会"回落"，
> 实际它们属性在闭集内，**被引擎直接抢走判定了**。

### v2 → v3：抽取器四条规则（92% → 94%）

| 规则 | 针对的失败 |
|---|---|
| 对象不同就不是同一个属性（表格/表头 ≠ 卡片/页面），宁可 `unknown` 也不错归 | 「表格行内边距」被归进「卡片内边距」 |
| 字符串取值只填取值本身 | `value` 被填成整句，锚定正则失配 |
| 一句多属性拆成多条 claim | 「variant 有默认值」+「size 无默认值」被合并 |
| 只填文档明确给出的信息 | `defaults` 被推断补齐 |

同时修了一个**真实的 KB 缺陷**：`COLOR-003` 的 must-match 正则把语义段限死为 6 类语义色，
而规则原文只说「形如 `color-<用途>-<语义>`」，导致合规 token `color-border-subtle` 被判违规。

> 这是引擎的独特产出 —— 确定性判定把"规则原文"与"params"的不一致暴露出来，
> 而 LLM 路径只会给一个模糊的失败理由。

### v3 → v4：例外粗筛加英文标识符（94% → 96%）

`COMP-001` 的例外写「纯布局容器（Container / **Divider**）不声明 size 与 variant」，
陈述是「属性声明**分割线 Divider** 未声明 size 与 variant」。
中文 3-gram 只重合 1 个（"声明与"），低于阈值 → 漏检 → 判 `fail`。**这是唯一的误报。**

修法：在中文 n-gram 之外加"英文标识符"信号，但**必须排除规则正文里已出现的通用词** ——
`size`/`variant` 在例外和正常陈述里都出现，纳入匹配会立刻制造假阳性
（全字符 4-gram 版本实测有 2/30 假阳性）。只认「正文里没出现过」的标识符后：

| 指标 | 修前 | 修后 |
|---|---|---|
| 排除型命中 | 8/10 | **10/10** |
| 正常用例假阳性 | 0/88 | **0/88** |
| 全量准确率 | 94% | **96%** |
| 误报 | 2 | **1** |

## 三、v5：切换默认引擎（97%，误报 0）

### 最后一处"误报"其实是标注缺陷

v4 剩的 1 处误报 + 1 处未命中同源于 `G20`。查下去发现问题不在系统，在**标注**：

| 案例 | 文档语义 | 标注 |
|---|---|---|
| `E053` | variant 有默认值、size 缺默认值 | **1 点，expect fail** |
| `G20` | 同上（措辞不同） | **2 点：variant→pass、size→fail** |

同一语义两种标注。而 `COMP-004` 要求「size 与 variant **都必须**有默认值」——
文档违反了它，**文档级结论就是 fail**。「variant 默认值 primary 正确」是**子观察**，
不是独立合规点。

我当初把 G20 拆成两点，是因为模型把一句话分解成了两条 ——
**那是让 fixture 适应模型，而不是适应规则。** 现已按 E053 对齐为单点
（总点数 120 → 119），并把这个理由写进该判定点的 `why` 字段。

> 所以那处误报**从来不是系统缺陷，是测量缺陷**。修完后误报 0、准确率 97%。

### 补齐切默认的前置条件：引用出处与修改建议

切引擎前发现一个不能忽略的缺口：引擎原始输出只有 `field / expected / actual`，
**没有 `evidence`（规范原文）和 `suggestion`（修改建议）** ——
而 README 承诺的输出是「结构化报告 + 引用出处 + 修改建议」。
直接切会让判定更准但**产物更差**。

补的方式是确定性的（不额外调模型）：引擎本来就加载了 `rule.statement`，
直接作引用出处；修改建议由 `field / expected / actual` 拼模板，字段名转中文标签，
并附上规则例外条款。

### 切换决定

三条门槛同时成立：**准确率 97% ≥ 95%、误报 0、过度拒答 0**。

```
CLI 默认引擎 = hybrid    （--engine llm 可回滚）
```

**回滚路径保留**：`python cli.py <doc> --engine llm` 走原纯 LLM 路径；
两条路径的评测脚本都还在，随时可对照。

## 四、此前的判断过程（保留，说明门槛是怎么被逐条满足的）

我此前写的门槛是 **准确率 ≥95% 且误报 0**。v4 时是：

- 准确率 ✅ 96% ≥ 95%
- 误报 ❌ 1 > 0（当时以为根因是判定粒度）

**所以当时没有切换。** 后来的诊断表明那处误报是标注缺陷而非系统缺陷，
修正后才达到门槛。

### 为什么误报门槛设成 0 而不是 ≤2

误报的危害是不对称的：一次"你合规却被判违规"会让设计团队下次不再相信这个工具；
而过度拒答只是多一次人工确认。**P0/P1 的优先级差别就来自这个不对称。**

### 但双路的实质优势已经确立

```
过度拒答：4 → 0        （引擎不会因为"措辞不对应"就拒绝判定）
确定性判定：0% → 78%   （可被单元测试锁定，不随模型版本/温度漂移）
错误可定位：field / expected / actual
```

而且它是**在准确率不下降的前提下**拿到的 —— 这才是本轮真正的结论。
