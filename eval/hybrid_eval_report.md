# 全量评测：双路并行（引擎 + LLM）vs 纯 LLM 路径

**任务**：把规则引擎与 LLM 路径并行接入，跑 120 个判定点，看是否比现状更好。

**结论：92%（111/120），比纯 LLM 路径的 95% 低 2pp。**
但引擎承担了 **81% 的判定**（97/120），把大部分判定变成了确定性的。
剩余错误高度集中在**抽取层**（属性误分类 + 取值带了整句），这是最新、最未调优的一层。

复现：`python -m eval.run_hybrid_eval`（约 10 分钟）

---

## 一、结果

| 指标 | 纯 LLM 路径（v5） | 双路并行 | 差 |
|---|---|---|---|
| 覆盖率 | 100% | 99% | -1pp |
| **端到端准确率** | **95%**（114/120） | **92%**（111/120） | **-2pp** |
| 误报 FP | 0 | **4** | +4 |
| 漏报 FN | 0 | 1 | +1 |
| 过度拒答 | 4 | **0** | -4 |
| 过度自信 | 2 | 3 | +1 |

**判定来源分布：引擎 97（81%）· LLM 26（22%）· 回落 0。**

按类别：

| 类别 | 准确率 | 引擎 | LLM |
|---|---|---|---|
| name / typo | **100%** | 12 / 19 | 0 |
| spacing | 96% | 22 | 1 |
| color | 95% | 16 | 3 |
| comp | 89% | 19 | 0 |
| no_coverage | 82% | 3 | 14 |
| **excluded（排除型）** | **80%** | 2 | 8 |

## 二、两次修正，一次预测失误

### 第一跑：87%，排除型从 10/10 掉到 2/10

我在上一份报告里预测"排除型会回落"，但**机制预测错了**：
它们根本没有回落 —— 属性（如 `卡片内边距`）在闭集内，**被引擎直接抢走判定了**。
引擎不读 `exceptions`，于是「全屏沉浸式视图内的卡片内边距 8px」被判 `fail`，
正确答案是 `pass`（被 SPACING-001 的例外排除）。

**修法**：在引擎判定之前加"例外粗筛" —— 用中文 3-gram 重合度判断陈述是否落在例外里，
命中就交回 LLM 路径。

### 例外粗筛的两轮迭代

| 版本 | 排除型命中 | 正常用例假阳性 |
|---|---|---|
| v1：全字符 4-gram | 8/10 | **2/30** ❌ |
| **v2：仅中文 3-gram** | **8/10** | **0/88** ✅ |

v1 的假阳性来自 `size`/`variant`/`Container` 这些拉丁词在正常陈述里也出现，
参与了 n-gram 计算。只保留中文并与「例外条款」做 3-gram 重合后，
假阳性归零。

> 这个细节值得记：**中文规范文本里夹带的英文术语是特征工程的陷阱。**
> 它们在例外条款和正常陈述里都会出现，本身不携带"是否被排除"的信息。

### 全量效果：87% → 92%

排除型 2/10 → 8/10，整体 +5pp。

## 三、剩余 9 处错误：几乎全在抽取层

| # | 案例 | 现象 | 根因 |
|---|---|---|---|
| 1 | `COMP-004` variant 默认值 | 期望 pass → fail | **判定粒度**：文档一句里同时有"variant 有默认值"（合规）和"size 无默认值"（违规），引擎按整句判 fail；评测要求按属性分开判 |
| 2 | `COMP-004` size 默认值 | 期望 fail → pass | 抽取器给的 `defaults` 字段不完整 |
| 3 | `COLOR-003` 语义 token | 期望 pass → fail | **抽取带整句**：`value` 给成了"颜色引用颜色引用 color-border-subtle 语义令牌。"，锚定正则自然不匹配 |
| 4 | `COLOR-003 例外` 品牌 Logo | 期望 pass → fail | 例外粗筛漏掉（措辞距离：陈述"位图内部" vs 例外"位图资源内部"） |
| 5 | `COMP-001 例外` Divider | 期望 pass → fail | 例外粗筛漏掉（陈述"分割线 Divider" vs 例外"Container / Divider"） |
| 6 | 表头间距 12px | 期望 uncertain → pass | **属性误分类**：归到了「元素间距」，而它是无覆盖对象 |
| 7 | 表格行内边距 8px | 期望 uncertain → fail | **属性误分类**：归到了「卡片内边距」 |
| 8-9 | 其余两处 | — | 同类 |

**7 处里 5 处是抽取层的锅**（属性分类错误、取值带整句、字段不全），
1 处是例外粗筛的召回不足，1 处是判定粒度与评测粒度不一致。

**没有一处是规则引擎算错。** 引擎在它该管的范围内是可靠的。

## 四、判断：当前不适合替换，但方向成立

### 不该现在就切默认路径

准确率 95% → 92% 是净退步。而且误报从 0 涨到 4 —— 对设计团队来说
"合规被判违规"会导致无谓返工，体验损失比"判不出来"更大。

### 但这个结果支持继续做

| 维度 | 现状 | 双路 |
|---|---|---|
| 准确率 | 95% | 92% |
| **判定可复现性** | 低（多次记录到同输入不同输出） | **81% 的判定是确定性代码** |
| 过度拒答 | 4 | **0** |
| 错误是否可定位 | 模型给理由，难以追溯 | 引擎给出 `field/expected/actual` |
| 改进方式 | 调提示词（已试三轮，收益递减） | **修抽取器**（第一版，未调优） |

**关键判断：双路的错误集中在最年轻、最未调优的组件（抽取器），
而纯 LLM 路径的错误集中在反复试过三轮都没解决的判定器。**
前者的改进空间明确且可测量，后者已经证明是收益递减的。

## 五、下一步（按预期收益排序）

| 顺序 | 动作 | 依据 |
|---|---|---|
| **1** | **修抽取器**：①`value` 只给取值本身，不带整句 ②属性分类加"未知就填 unknown"的强约束 ③`defaults` 必须给全 | 7/9 错误的直接原因 |
| 2 | 例外粗筛提召回（现在是中文 3-gram，可加同义词扩展或降低阈值＋二次确认） | 2/9 错误 |
| 3 | 判定粒度对齐：一句多属性时按属性拆判定 | 1/9 错误 |
| 4 | 再跑全量，目标 ≥95% 且误报 ≤1 | 达标才考虑切换默认路径 |

### 一个必须避免的诱惑

**不要把"按属性拆判定"做成正则切分。** 第 3 项错误的本质是
"一句话里有多个受不同约束的属性"，正解是让抽取器就产出多条 claim，
而不是让引擎去切句子。引擎不擅长自然语言切分，这也是本项目反复踩到的边界。
