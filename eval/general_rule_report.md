# 实验报告：修复「通用规则 + 特定子对象」误拒

**要修的问题**（来自 `generation_report.md` 三、）：

> 两处错误都是同一类：`COLOR-003`（色彩必须用语义 token）、`TYPO-003`（字重白名单）
> 这类**对所有对象生效的通用规则**，在问及某个特定子对象
> （"按钮文字色"/"注释文字字重"）时被判为不适用 → 过度拒答。

**结论：根因不是判定器，是检索判定的截断。修复后 40/40 = 100%（连续 3 次复现）。**

复现：`python -m eval.probe_general_rule`（诊断）· `python -m eval.run_generation_eval`（效果）

---

## 一、先诊断，再动手（这一步救了整轮工作）

前几份报告的教训（尤其 `structured_report.md` 推翻了 `e2e_report.md` 的根因判断）
说明：**确认根因之前不要动判定器。** 所以先写诊断脚本，把三种可能分开：

| 可能 | 含义 | 该改什么 |
|---|---|---|
| A | 检索层根本没取到通用规则（不在 top-10） | BM25 / 索引 |
| B | 取到了，但被 funnel 截断（只判 top-2） | 判定范围 |
| **C** | 取到了、也判了，但判为不适用 | 判定器 / 提示词 |

### 诊断结果

```
【G08】主按钮文字颜色的取值是否必须使用语义令牌   本应适用：COLOR-003
  排名  section        BM25   相关性判定
  1   CASE-005        37.2   [1] 案例讲背景色引用色阶，未涉及文字颜色取值
  2   NAME-004        35.8   [1] 仅讲令牌命名格式
  3   COLOR-003       33.2   [3] 规则明确要求颜色引用须用语义token，覆盖主按钮文字颜色  ←gold
  4   COLOR-003       31.7   [3] 规则要求所有颜色引用语义token，直接覆盖                    ←gold
  → 根因 B：取到了但被 funnel 截断 —— gold 排第 4，而只对 top-2 做判定

【G14】辅助注释文字允许使用哪些字重              本应适用：TYPO-003
  1   CASE-009        32.7   [1] 资料讲标题字重，未答辅助注释允许字重

  5   TYPO-003        16.4   [2] 资料给出字重三档及用途，需推导          ←gold
```

**判定器一直是对的** —— 它对 `COLOR-003` 给了 **3 分**（"直接覆盖主按钮文字颜色"），
对 `TYPO-003` 给了 2 分。是我的 `max_judge=2` 让它**根本没看到该看的规则**。

> 这类错误最危险的地方：它伪装成"判定器不够好"。
> 如果直接去改提示词（我在 `relevance_report.md` 里已经这么错过一次），
> 会把一个检索截断问题误诊成提示词问题，然后越改越糟。

## 二、修复：放宽判定范围 + 早期退出

```python
# 改前：只判 top-2
for c in candidates[:2]: ...

# 改后：判到 max_judge=5，但一旦拿到满意结果就停
for c in candidates[:max_judge]:
    score = judge(c)
    if score >= min_relevance:
        passed.append(c)
        if score >= 3 or len(passed) >= 2:   # 早期退出
            break
```

**为什么早期退出一开始就设计进去**：无脑把判定数从 2 提到 5 会让成本涨 150%。
而实测中简单查询通常 rank 1 就命中 3 分 —— 早期退出让**简单查询比原来更便宜**（1-2 次判定），
只有难题才付到 5 次。实测 `judged` 值：G08 用了 4 次、G14 用了 5 次、排除型用例只用 1 次。

### 然后我主动把评测集改难了

100% 出现后我没有直接汇报，而是先做了一件事：**往最容易通过的方向反着补题**。

因为对照测试暴露了一个问题：我的 3 个 `no_coverage` 用例（圆角 / 投影 / 动效）
**词面距离太大**，BM25 本来就召不回东西，当然能拒答。真正难的是**词面重叠**的无覆盖：

| 新增难例 | 为什么难 | 结果 |
|---|---|---|

| G34 表头与首行间距 12px | "间距"直接命中卡片间距规则 | ✅ uncertain |
| G35 卡片边框宽度 1px | 1px 易让人联想间距阶梯 | ✅ uncertain |

**4 个难例全部通过。** 期间发现 G32/G35 的原表述（"单独定义一套色值""单独取值"）
**隐含了违反 COLOR-003**，模型判 fail 其实是对的 —— 是我的 fixture 有歧义，已改用
不隐含违规的对象（分隔线样式 / 边框宽度）。

## 四、这个 100% 有多可信（必须说清楚）

### 置信区间仍然宽

40/40 的 Clopper-Pearson 95% 置信区间约 **[93%, 100%]**。
**准确讲法是"40 个判定点全部正确，95% CI [93%, 100%]"，不是"准确率 100%。"**
单个失败就会把它拉到 97.5%。

### 三次复现降低了"运气好"的可能

今天共跑 6 次完整评测：修复前 4 次（80% → 86% → 94% → 94%）、
修复后 1 次（36/36）、加难例后 1 次（98% → 修正 fixture 后）、
最终连续 3 次 40/40。**修复后的 3 次全为 100%，是本次最重要的稳定性证据。**

### 但观察到真实的判定波动

G32 在改写前**同一份文档两次运行给出不同判定**（一次 uncertain、一次 fail）。
说明 `temperature=0` 下判定器仍有波动 —— 这次是通过**消除 fixture 歧义**规避的，
不是靠提升判定器的确定性。

### 剩余限制

- **40 个判定点仍是小样本**，且文档都极短（1-2 句）。
- **评测集由我编写**：虽然期望值都从规则 params 推导，但选择哪些规则、如何表述，
  仍受我的理解影响。真实规范库的边界情况更杂。
- **无覆盖用例只有 7 个**，且都是我自己设计的；`COLOR-003` 这类"宽泛规则"
  的边界可能还有未覆盖到的形态。

## 五、这一轮的真正价值

不是"修到 100%"，而是：

1. **诊断先于修复**。如果直接改提示词，会沿着错误方向迭代 ——
   而这个项目已经犯过一次同类错误（`relevance_report.md` 的三轮提示词迭代）。
2. **修复带来的是"看得见该看的规则"，而不是"放宽判定标准"**。
   `max_judge` 从 2 到 5 没有降低任何标准，只是不再把正确答案挡在门外。
3. **100% 之后主动加难**。评测集的价值在于暴露问题，而它会不自觉地避开你方法的弱点 ——
   这句话现在在 `e2e_report.md`、`generation_report.md` 和本报告里各出现一次，三次都被证实。

## 六、下一步

| 优先级 | 动作 | 理由 |
|---|---|---|
| 1 | 评测集扩到 100+ 判定点 | 当前 CI 仍宽 [93%, 100%] |
| 2 | 加长文档用例（分段 / 截断行为） | 全部文档只有 1-2 句，未测长文 |
| 3 | 让判定器更确定（结构化输出 + 多票） | G32 暴露过同输入不同判定 |
| 4 | LangGraph 迁移 + checkpointer | 面试考点，但属"补框架"而非"补能力" |

### 一个仍未解决的隐患

`max_judge=5` 意味着判定成本上限是原来的 2.5 倍。虽然早期退出让常见情况更便宜，
但**最坏情况的成本没有测**。真实部署需要统计 `judged` 的分布，
并考虑给难查询设预算上限。
