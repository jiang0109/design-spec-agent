# design-spec-agent

输入一份设计文档，agent 对照**设计规范知识库**做逐条合规判定，
输出**可校验的结构化报告 + 引用出处 + 修改建议**；
规范未覆盖时**明确拒答**，而不是编一个看起来合理的结论。

> **当前状态：Week 2 完成 + 生成层端到端评测（119 判定点）+ 双路判定引擎默认启用**
> 真实知识库（38 条）· 分块策略评测 · 检索层拒答 · **生成层 97%（双路，含规则引擎）**
> 下一步：提升 BM25 排序质量、LangGraph 迁移。

---

## 它解决什么问题

设计规范的落地检查长期依赖人工 review：慢、口径不一致、无法规模化。
但"用 LLM 做这件事"有个致命前提 —— **它必须能说"我不知道"**。

知识库有覆盖盲区是常态。如果 agent 用"卡片内边距"规则去回答"表格行内边距"的问题，
产出的是**看起来完全合理、但完全错误**的判定，这比不做检查更危险。

所以本项目在三个层次上都做了降级设计，每一层都带**可解释的原因**：

| 层次 | 机制 | 实测证据 |
|---|---|---|
| 生成层 | 无依据判 `uncertain`，不猜 | 知识库无覆盖时 3 项全判 uncertain，零编造 |
| 检索层 | LLM 相关性闸门，识别"词对上了但答不了" | BM25 无法拒答（信号方向还是反的），闸门可分离 |
| 拒绝原因 | 区分「被规则明确排除」与「知识库无覆盖」 | 表格行高由误判 `fail` 修正为 `pass` |

## 快速开始

```bash
# 1. 装依赖
python -m venv .venv && .venv\Scripts\activate
pip install "openai>=1.40" "pydantic>=2.7" "python-dotenv>=1.0"

# 2. 配置 API key（见下节）
copy .env.example .env

# 3. 自检
python cli.py --ping

# 4. 冒烟测试（离线，零 API 调用，约 2 秒）
python -m eval.test_smoke

# 5. 跑一份示例文档
python cli.py samples/sample_doc.md -v
```

输出落在 `out/`：`*.report.json`（结构化结果）与 `*.report.md`（人读版本）。

## 架构

```
                设计文档 (.md)
                      │
                      ▼
      ┌───────────────────────────────┐
      │  agent 循环（src/agent.py）     │
      │  手写 ReAct：LLM + 工具        │
      │  + 消息历史 + 终止条件          │
      └───────────────┬───────────────┘
                      │ tool_call
                      ▼
      ┌───────────────────────────────┐
      │  两级检索（src/tools.py）       │
      │  ① BM25 粗排 top-10   （便宜）  │
      │  ② LLM 相关性判定 top-2（贵）   │
      └───────────────┬───────────────┘
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
   found=true     excluded      no_coverage
   有适用规范     被规则明确排除   知识库无覆盖
        │             │              │
        ▼             ▼              ▼
   判 pass/fail    判 pass       判 uncertain
                             （not_applicable 同此）
```

|---|---|---|---|---|---|---|

### 关键优化：分块粒度（可证伪预测已验证）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `heading` 均长 | 1043 字符 | 478 / 392 字符 |
| 达到饱和所需上下文 | 4000 字符 | **2000 字符** |
| 未饱和区间命中率 | 58~83% | **75~92%**（+8~17pp） |

根因：**正文平均只有 395 字符**，撑大 chunk 的是 front-matter 参数块（占 58%），
而其中 60% 与正文重复。精简参数（589→136 字符，压缩 74%）+ 按粗体标签二次切分。

### 生成层端到端（119 个判定点，115 份文档）

期望判定**全部由知识库规则的 params 推导**，不参考 agent 输出。
数据集分两半：**40 个手写难例**（自然措辞、刻意边界）+ **80 个参数驱动生成**
（探针表只写数据，模板渲染成文档 —— 保证可复现且不因人引入歧义）。

仓库里有两条判定路径，**默认跑第一条**（`--engine` 可切换）：

| 路径 | 说明 | 准确率（119 点） | 误报 | 过度拒答 | 确定性判定占比 |
|---|---|---|---|---|---|
| **默认：双路并行（hybrid）** | 抽取 → 属性路由 → 规则引擎；未知/例外回落 LLM | **97%**（116/119） | **0** | **0** | **76%** |
| 备选：纯 LLM | `run_agent` → 检索 → 相关性闸门 → LLM 判定 | 93%（111/119） | 1 | 4 | 0% |

切换依据是三条同时成立：**准确率 ≥95%、误报 0、过度拒答 0**。

> ⚠️ **不要把这个 4pp 差距当成"双路更准"。** 纯 LLM 路径在 119~120 点上多次测得
> **93%~96%**（差异几乎全在「过度拒答」），两条路径的单次测量区间高度重叠。
> 真正可靠的优势是：**误报 0、过度拒答 0、76% 的判定由确定性代码完成**（可被单元测试锁定，
> 不随模型版本/温度漂移）。详见 `eval/hybrid_eval_report.md`。

## 设计决策

- **为什么先手写循环再上框架**：agent 的本质只有 LLM + 工具 + 消息历史 + 终止条件四件事。
  先手写一遍再迁到 LangGraph，才能说清框架封装了什么、代价是什么。
- **为什么要结构化输出契约**：自然语言无法被程序可靠消费。用 Pydantic 定义字段与取值约束，
  校验失败时把错误原文回喂给模型自动修正 —— 这是"鲁棒性"的工程含义。
- **为什么区分 pass / fail / uncertain**：检索不到依据时宁可判 uncertain 也不猜。
  误报和漏报都是质量问题，而"承认不知道"是可控性的前提。
- **为什么两侧都要护栏**：`max_steps` 限制轮次，`max_tool_calls` 限制调用总数。
  实测 `max_steps=1` 时模型仍在单轮里发出 6 个并发调用 —— 只靠步数上限拦不住费用。
- **为什么拒绝原因要三值而不是布尔**：`found=false` 混合了两种语义完全相反的情况 ——
  "规则明确排除该对象"（有结论，应判 pass）与"知识库无覆盖"（应判 uncertain）。
  一个布尔值承载不了，必须结构化传递。
- **为什么用 BM25 而不是向量检索**：设计规范是术语密集的结构化文本，正是 BM25 的强项；
  35 题上召回已达 100%，检索精度不是当前瓶颈。真正需要语义能力的地方
  （拒答判断）已用 LLM 相关性判定解决。
- **为什么相关性判定要判 top-5 而不是 top-2**：只判 top-2 会让「通用规则 + 特定子对象」
  的查询被系统性误拒 —— 通用规则常排在第 3-5 名（如 `COLOR-003` 排第 4）。
  实测那是**检索截断**问题，不是判定器问题。现在判到 5 名但带早期退出，
  简单查询反而更便宜。

## 已知限制

- **知识库只有 23 条规则 / 40,000 字符**，混淆压力低于真实规范库（150-400 条）。
  方向性结论可信，具体数值不应外推。
- **生成层准确率 94%（113/120），但同一代码多次测得 93%~96%**，波动几乎全在
  「过度拒答」。这是引入规则引擎（确定性判定）的核心动机 ——
  `temperature=0` 无法消除判定器的运行间波动。
  判定器在 `temperature=0` 下仍有波动，同一输入可能给出不同判定。
- **文档都很短**（1-2 句），未测长文档的分段 / 截断行为。
- **判定成本已到上限**：相关性判定范围已放宽到 top-10（funnel 全量），
  早期退出让常见查询便宜，但难查询会判满 10 次。
  **不宜再扩大** —— 实测 5→10 的净收益只有 +1 个判定点，却引入了过度自信风险。
- **无向量检索**：术语鸿沟（"留白" vs "内边距"）无法靠词汇匹配跨过，
  `colloquial` 层所有配置都只有 75%。正解是 query rewriting，尚未实现。
- **闸门有成本**：每题额外 2 次（相关性）~3 次（含拒绝原因）LLM 调用，
  端到端实测耗时约 +2.9s/份。
- **相关性判定存在运行间波动**：`temperature=0` 未消除，边界题分数会翻转，
  阈值 2 是边界状态而非安全余量。
- **判定粒度**：一句话里含多个受不同约束的属性时（如「variant 默认值为 primary，
  但未声明 size 的默认值」），抽取器可能只产出一条 claim，导致两个判定点被压成一个。
  这是双路分支**唯一剩余误报**的根因；纯 LLM 路径不受影响（它按文档逐点判）。
  真实设计文档常常一段多属性，所以这个缺陷在真实使用中会比在评测集里更常见。
- **单轮执行，无持久化**：进程中断即丢失中间状态（Week 3 引入 checkpointer）。

### 一个容易踩的语义差异

`excluded` 型结论（"该对象被规则明确排除"）的 **`evidence` 字段为空是设计使然** ——
排除型结论没有规范原文可引用，它是一个"不存在约束"的判断。

因此**不要用「evidence 为空 = 可疑」做下游校验**：那会把正确的 `pass` 误判成问题。
判断依据应看 `verdict` 是 `pass` 且 `reason` 说明了被哪条规范排除。

**共同的教训是：错误的来源几乎都在"如何度量与解释"这一层，而不在业务逻辑里。**
