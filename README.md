# design-spec-agent

输入一份设计文档，agent 对照**设计规范知识库**做逐条合规判定，
输出**可校验的结构化报告 + 引用出处 + 修改建议**；
规范未覆盖时**明确拒答**，而不是编一个看起来合理的结论。

> **当前状态：Week 2 完成 + 生成层评测扩到 120 个判定点**
> 真实知识库（38 条）· 分块策略评测 · 检索层拒答 · **生成层 96%（115/120，零误报）**
> 下一步：提升 BM25 排序质量、LangGraph 迁移。

---

## 它解决什么问题

设计规范的落地检查长期依赖人工 review：慢、口径不一致、无法规模化。
但"用 LLM 做这件事"有个致命前提 —— **它必须能说"我不知道"**。

知识库有覆盖盲区是常态。如果 agent 用"卡片内边距"规则去回答"表格行内边距"的问题，
产出的是**看起来完全合理、但完全错误**的判定，这比不做检查更危险。

所以本项目在三个层次上都做了降级设计，每一层都带**可解释的原因**：

| 层次 | 机制 | 实测证据 |
|---|---|---|
| 生成层 | 无依据判 `uncertain`，不猜 | 知识库无覆盖时 3 项全判 uncertain，零编造 |
| 检索层 | LLM 相关性闸门，识别"词对上了但答不了" | BM25 无法拒答（信号方向还是反的），闸门可分离 |
| 拒绝原因 | 区分「被规则明确排除」与「知识库无覆盖」 | 表格行高由误判 `fail` 修正为 `pass` |

## 快速开始

```bash
# 1. 装依赖
python -m venv .venv && .venv\Scripts\activate
pip install "openai>=1.40" "pydantic>=2.7" "python-dotenv>=1.0"

# 2. 配置 API key（见下节）
copy .env.example .env

# 3. 自检
python cli.py --ping

# 4. 冒烟测试（离线，零 API 调用，约 2 秒）
python -m eval.test_smoke

# 5. 跑一份示例文档
python cli.py samples/sample_doc.md -v
```

输出落在 `out/`：`*.report.json`（结构化结果）与 `*.report.md`（人读版本）。

### 常用命令

| 命令 | 作用 | 是否调用 API |
|---|---|---|
| `python -m eval.test_smoke` | 全部离线不变量（9 项） | ❌ |
| `python -m eval.validate_kb` | 知识库结构校验 | ❌ |
| `python -m eval.run_eval` | 检索评测（5 种分块配置 × 双口径） | ❌ |
| `python -m eval.run_generation_eval` | **生成层端到端评测（36 个判定点）** | ✅ |
| `python -m eval.run_e2e` | 端到端：三类材料 × 闸门开关对照 | ✅ |
| `python -m eval.probe_reject_reason` | 拒绝原因分类 + 回归检查 | ✅ |

## 架构

```
                设计文档 (.md)
                      │
                      ▼
      ┌───────────────────────────────┐
      │  agent 循环（src/agent.py）     │
      │  手写 ReAct：LLM + 工具        │
      │  + 消息历史 + 终止条件          │
      └───────────────┬───────────────┘
                      │ tool_call
                      ▼
      ┌───────────────────────────────┐
      │  两级检索（src/tools.py）       │
      │  ① BM25 粗排 top-10   （便宜）  │
      │  ② LLM 相关性判定 top-2（贵）   │
      └───────────────┬───────────────┘
                      │
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
   found=true     excluded      no_coverage
   有适用规范     被规则明确排除   知识库无覆盖
        │             │              │
        ▼             ▼              ▼
   判 pass/fail    判 pass       判 uncertain
                             （not_applicable 同此）
```

### 模块职责

```

src/llm.py        模型客户端：唯一接触 API 的地方，附带 token 与耗时统计
src/tools.py      工具层：两级检索 + 相关性闸门 + 拒绝原因分类
src/relevance.py  LLM 相关性判定（0-3 分）与拒绝原因分类
src/agent.py      手写 ReAct 循环 + 校验重试 + 标记渲染
src/chunking.py   四种分块策略 + 结构化参数精简
src/retrieve.py   BM25（零依赖）+ 中文双粒度分词 + 标题字段加权
cli.py            命令行入口
kb/               设计规范知识库（38 条双通道条目）
eval/             评测集、评测脚本、实验报告
samples/          示例文档（含端到端三类对照材料）
```

### 知识库

| 文件 | 规则数 | 说明 |
|---|---|---|
| `kb/spacing.md` | 5 | 间距：内边距 / 间距 / 分组 / 页面外边距 / 组件内部 |
| `kb/color.md` | 5 | 色彩：对比度 / 语义色 / 状态色 |
| `kb/typography.md` | 4 | 字体：字号阶梯 / 行高 / 字重 / 正文默认 |
| `kb/component.md` | 5 | 组件属性：必填 / 命名 / 布尔前缀 / 默认值 / 变体 |
| `kb/naming.md` | 4 | 命名：图层 / 组件 / 禁止默认名 / 设计令牌 |
| `kb/cases.md` | 15 条案例 | 历史违规「违规 → 修正 → 经验」 |

**38 条 / 约 40,000 字符**，双通道：YAML front-matter（机器可判定）
+ Markdown 正文（叙事）。格式契约见 `kb/_format.md`。

### 分块策略（35 题评测集，等上下文预算 2000 字符）

| 配置 | chunk 数 | 均长 | 等预算命中率 |
|---|---|---|---|
| `fixed` 固定长度 | 58 | 301 | **100%** |
| `semantic` 段落聚合 | 41 | 399 | **97%** |
| `heading_split@300` | 72 | 392 | **97%** |
| `heading_split@500` | 45 | 517 | 88% |
| `heading` 原始按标题 | 38 | 1043 | 76% |

**差异几乎全部集中在 `confusable` 层**（同术语跨文档，如"属性名"vs"令牌名"）：

| 配置 | literal | value | colloquial | paraphrase | context | **confusable** |
|---|---|---|---|---|---|---|
| `fixed` | 100% | 100% | 100% | 100% | 100% | **100%** |
| `heading_split@300` | 100% | 100% | 75% | 100% | 100% | **100%** |
| `heading` | 100% | 100% | 75% | 50% | 80% | **64%** |

`literal` / `value` / `context` 三层所有配置都是 100% —— **不提供任何区分信息**。
要判断分块策略优劣，必须看 `confusable` 层。

### 关键优化：分块粒度（可证伪预测已验证）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `heading` 均长 | 1043 字符 | 478 / 392 字符 |
| 达到饱和所需上下文 | 4000 字符 | **2000 字符** |
| 未饱和区间命中率 | 58~83% | **75~92%**（+8~17pp） |

根因：**正文平均只有 395 字符**，撑大 chunk 的是 front-matter 参数块（占 58%），
而其中 60% 与正文重复。精简参数（589→136 字符，压缩 74%）+ 按粗体标签二次切分。

### 拒答能力

| 信号 | 可答均值 | 可答最小 | 无覆盖最大 | 可分？ |
|---|---|---|---|---|
| BM25 top1 分数 | 33.3 | 13.9 | **34.5** | ❌ 方向相反 |
| LLM 相关性分 | 2.97 | 2 | 1 | ✅ |

**BM25 的分数在拒答问题上不仅无用，而且方向是反的** ——
无覆盖题的 top1 分数比可答题的最小值还高，因为词面重合仍然存在。

### 溯源与预算护栏

| 指标 | 结果 |
|---|---|
| 引用出处被模型改写（溯源漂移） | 47% → **0%**（加严提示 + 指标检测） |
| 工具调用总预算 | 预算=2 时 4 个未查证点全判 uncertain，零编造 |
| 校验重试 | 结构化输出失败时回喂错误原文自动修正 |

### 生成层端到端（120 个判定点，115 份文档）

期望判定**全部由知识库规则的 params 推导**，不参考 agent 输出。
数据集分两半：**40 个手写难例**（自然措辞、刻意边界）+ **80 个参数驱动生成**
（探针表只写数据，模板渲染成文档 —— 保证可复现且不因人引入歧义）。

| 指标 | 数值 |
|---|---|
| 覆盖率（模型给出判定） | **100%**（120/120） |
| **端到端准确率** | **96%**（115/120） |
| 误报 FP（合规→违规） | **0** |
| 漏报 FN（违规→合规） | 2 |
| 过度拒答（有依据却判 uncertain） | 3 |
| 过度自信（无覆盖却下结论） | **0** |

按类别：

| 类别 | 正确/总数 |
|---|---|
| comp | 19/19 |
| **排除型**（规则明确排除该对象） | **10/10** |
| **无覆盖**（应诚实判 uncertain） | **17/17** |
| color · typo | 18/19 · 18/19 |
| name · spacing | 11/12 · 22/24 |

**5 处错误全部是真实缺陷、零工具缺陷**，分成两类：

- **判定器太严格（3 处）**：规则就在眼前仍被判为不适用。例如问"图层还是 Rectangle 45"，
  而 `NAME-003` 就是「禁止默认名称」，判定器却说"未涉及名称与内容一致性"。
- **生成层语义错误（2 处）**：① 只校验取值白名单、漏了"组间必须大于组内"这类**关系约束**；
  ② 把"允许的字号档位"当成"允许的默认字号"（`12px` 是允许的**字号**，
  但正文**默认字号**必须 14）—— 这是真实的语义滑移，改检索无济于事。

> ⚠️ **口径说明**：115/120 的 95% 置信区间约 **[91%, 98%]**。
> 判定器在 `temperature=0` 下仍有波动，96% 是 93%~97% 之间的一个点。
> 详见 `eval/generation_report.md`。

## 设计决策

- **为什么先手写循环再上框架**：agent 的本质只有 LLM + 工具 + 消息历史 + 终止条件四件事。
  先手写一遍再迁到 LangGraph，才能说清框架封装了什么、代价是什么。
- **为什么要结构化输出契约**：自然语言无法被程序可靠消费。用 Pydantic 定义字段与取值约束，
  校验失败时把错误原文回喂给模型自动修正 —— 这是"鲁棒性"的工程含义。
- **为什么区分 pass / fail / uncertain**：检索不到依据时宁可判 uncertain 也不猜。
  误报和漏报都是质量问题，而"承认不知道"是可控性的前提。
- **为什么两侧都要护栏**：`max_steps` 限制轮次，`max_tool_calls` 限制调用总数。
  实测 `max_steps=1` 时模型仍在单轮里发出 6 个并发调用 —— 只靠步数上限拦不住费用。
- **为什么拒绝原因要三值而不是布尔**：`found=false` 混合了两种语义完全相反的情况 ——
  "规则明确排除该对象"（有结论，应判 pass）与"知识库无覆盖"（应判 uncertain）。
  一个布尔值承载不了，必须结构化传递。
- **为什么用 BM25 而不是向量检索**：设计规范是术语密集的结构化文本，正是 BM25 的强项；
  35 题上召回已达 100%，检索精度不是当前瓶颈。真正需要语义能力的地方
  （拒答判断）已用 LLM 相关性判定解决。
- **为什么相关性判定要判 top-5 而不是 top-2**：只判 top-2 会让「通用规则 + 特定子对象」
  的查询被系统性误拒 —— 通用规则常排在第 3-5 名（如 `COLOR-003` 排第 4）。
  实测那是**检索截断**问题，不是判定器问题。现在判到 5 名但带早期退出，
  简单查询反而更便宜。

## 已知限制

- **知识库只有 23 条规则 / 40,000 字符**，混淆压力低于真实规范库（150-400 条）。
  方向性结论可信，具体数值不应外推。
- **生成层准确率 96%（115/120），95% CI 约 [91%, 98%]**，且为单次运行。
  判定器在 `temperature=0` 下仍有波动，同一输入可能给出不同判定。
- **文档都很短**（1-2 句），未测长文档的分段 / 截断行为。
- **判定成本已到上限**：相关性判定范围已放宽到 top-10（funnel 全量），
  早期退出让常见查询便宜，但难查询会判满 10 次。
  **不宜再扩大** —— 实测 5→10 的净收益只有 +1 个判定点，却引入了过度自信风险。
- **无向量检索**：术语鸿沟（"留白" vs "内边距"）无法靠词汇匹配跨过，
  `colloquial` 层所有配置都只有 75%。正解是 query rewriting，尚未实现。
- **闸门有成本**：每题额外 2 次（相关性）~3 次（含拒绝原因）LLM 调用，
  端到端实测耗时约 +2.9s/份。
- **相关性判定存在运行间波动**：`temperature=0` 未消除，边界题分数会翻转，
  阈值 2 是边界状态而非安全余量。
- **单轮执行，无持久化**：进程中断即丢失中间状态（Week 3 引入 checkpointer）。

### 一个容易踩的语义差异

`excluded` 型结论（"该对象被规则明确排除"）的 **`evidence` 字段为空是设计使然** ——
排除型结论没有规范原文可引用，它是一个"不存在约束"的判断。

因此**不要用「evidence 为空 = 可疑」做下游校验**：那会把正确的 `pass` 误判成问题。
判断依据应看 `verdict` 是 `pass` 且 `reason` 说明了被哪条规范排除。

| 报告 | 内容 | 结论 |
|---|---|---|

| `eval/pilot_report.md` | 10 题校准：语料是否够用 | 双口径给出相反信号，差异 30pp |
| `eval/rerank_report.md` | 标题字段加权 rerank | **假设被推翻**：0 提升，真瓶颈是粒度 |
| `eval/granularity_report.md` | 分块粒度修复 | **可证伪预测成立**，+17pp |
| `eval/retrieval_report.md` | 扩到 35 题评测集 | 区分力恢复 27pp；发现检索层无法拒答 |
| `eval/relevance_report.md` | LLM 相关性判定 | 拒答可行；记录判定波动 |
| `eval/e2e_report.md` | 端到端接入与验证 | 零收益 + 一次真实回归 |
| `eval/structured_report.md` | 结构字段（例外）实验 | **推翻上一份的根因判断** |
| `eval/reject_reason_report.md` | 拒绝原因分类 | **回归修复**，3/3 预注册判据通过 |
| `eval/generation_report.md` | 生成层端到端（120 判定点） | **96%（115/120）**，5 处错误全为真实缺陷 |
| `eval/general_rule_report.md` | 修「通用规则 vs 子对象」误拒 | **根因是判定截断，非判定器** |

这些报告记录了七次「结论被自己的验证推翻」：
指标字段名写错 → 选错度量口径 → 浮点阈值判错 → 根因误判（评测集坏题）→
结论前提未验证 → 统计工具假阴性（四轮修匹配）→ 根因误判（把截断当成判定器问题）。
**共同的教训是：错误的来源几乎都在"如何度量与解释"这一层，而不在业务逻辑里。**
